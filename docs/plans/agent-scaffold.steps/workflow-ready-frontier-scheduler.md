### `workflow-ready-frontier-scheduler`: add the workflow driver's read-only ready-frontier scheduler after the typed fleet (`Q-82`, Stage 3)

This focused sidecar is the implementation authority for Stage 3. The canonical Q-51 architecture remains design context and is aligned to this contract; where an older exploration used broader "nonterminal" language or treated task actions as frontier members, this sidecar's domain and precedence rule control. Q-82 authorises the scheduler after the typed fleet and keeps scheduler authority out of the first visibility repair.

THE PROBLEM. Once every active unit is visible and typed, the compatibility pending selector still chooses only one lowest-order pending action and serialises independent ready work. Choosing every nonterminal step naively is also wrong: it can schedule dependencies together, treat `deferred` or `optional` as ready, hide an active task action, or turn a read-only adviser into an executor.

ONE ELIGIBLE-STEP DOMAIN. `ready_frontier` is step-only and computed over Roadmap steps whose status is exactly `not-started` or `next`. Such a candidate is ready exactly when every `blocked_by` target resolves and has status `complete` or `skipped`; `in-progress`, `not-started`, `next`, `optional` and `deferred` blockers do not satisfy the dependency. The frontier contains every ready candidate in Roadmap declaration order, once. In-progress exploration, implementation and work-review actions are active-unit actions, not ready-step candidates. Task plan review, acceptance and standalone review and question-scoped exploration are also active-unit actions outside the step frontier. Increments carry no DAG edge and never enter this domain.

TASK/ACTION PRECEDENCE AND SERIAL FALLBACK. The typed fleet first exposes explicit active units in their declared order. If one has an actionable instruction, `selected_action` remains the first such active-unit action; a task-scoped acceptance or plan review, a question exploration or an active step review therefore keeps focus even when independent pending steps appear in `ready_frontier`. The scheduler still reports those pending candidates as advisory parallel opportunities, but it does not replace the active instruction. Only when no explicit active unit is actionable does `selected_action` become the first `ready_frontier` member, replacing `workflow-loop-visibility`'s one-step pending fallback. Consequently the selected-action membership invariant is conditional: a frontier-selected action must be a byte-for-byte member of `ready_frontier`; an explicit active-unit selection is a member of `active_units` and need not appear in the frontier.

Project the frontier and selection origin on JSON and human surfaces. Human output names the one serial action separately from the remaining advisory parallel candidates. The tool never spawns, reserves, leases, mutates or merges work; the orchestrator decides whether its isolation budget permits any proposed fan-out.

No increment-level DAG, resource allocator, priority score, daemon, persisted lease or automatic merge enters this step. The plan's step graph is the only scheduling graph.

### Increment 1, `workflow-ready-frontier-scheduler-inc1`

RISK CLASS `risky` (two consecutive clean review rounds). Agents act on scheduler advice, so an invalid frontier can start work before its dependency or fan out conflicting authority. The function is pure and read-only, which makes exhaustive fixture testing possible but does not reduce the consequence of wrong advice.

ACCEPTANCE.

1. One table-driven eligibility suite covers independent ready steps, a dependency chain, a diamond, unresolved blockers, blockers in every Roadmap status, terminal candidate steps, and no-ready-work. It proves the only candidate statuses are `not-started` and `next`, and every frontier is declaration ordered and duplicate-free.
2. A `complete` blocker and a `skipped` blocker both satisfy the edge. Red mutations that require strict `complete`, accept `optional`/`deferred`, or treat scheduled/in-progress blockers as satisfied fail focused fixtures.
3. The frontier is maximal over that one domain: returning only the first ready step fails an independent/diamond fixture, and returning every nonterminal step fails dependency and status fixtures.
4. Explicit active-unit precedence is pinned. A task-scoped acceptance plus independent pending work selects acceptance while reporting the pending frontier beside it; an active work-review plus independent pending work selects the review; a question-scoped exploration behaves the same. None is coerced into a frontier member or rewritten as a generic worker action.
5. When no explicit active unit is actionable, `selected_action` is the first frontier member byte-for-byte after JSON decoding and the remaining members are parallel candidates. Human output identifies this as the serial fallback. A one-ready-step fixture produces the same planner action as the pre-scheduler pending fallback.
6. Membership is conditional and tested on both branches: a frontier-origin selection absent from `ready_frontier` fails; an active-unit-origin selection absent from `active_units` fails; task acceptance with a non-empty frontier is valid and must not be rejected by the frontier-membership guard.
7. Active review, skipped-blocker, task-acceptance-with-pending-work and serial-fallback fixtures are golden on both human and JSON surfaces. Existing visibility/typed-fleet phase actions and declared risk-class output stay unchanged.
8. Determinism holds across runs and machines. No wall clock, filesystem lock, model capacity or worktree availability changes the pure frontier.
9. No command writes the plan, metrics, ledger or worktree; no spawn/merge API is added. Red path review rejects `driver/record.rs`, a daemon or an increment-level scheduler.
10. README documents advisory frontier semantics, active-action precedence, skipped blockers and serial fallback; the canonical architecture summary points to this focused authority; `CHANGELOG.md` records the new output. Pack guidance changes only if it currently implies exactly one ready step may exist.
11. Both validation modes, strict render, tests including red mutations, Clippy, diff checks and ASCII checks pass.
