### `workflow-ready-frontier-scheduler`: add the workflow driver's read-only ready-frontier scheduler after the typed fleet (`Q-82`, Stage 3)

This focused sidecar is the implementation authority for Stage 3. The canonical Q-51 architecture remains design context and is aligned to this contract; where an older exploration used broader "nonterminal" language or treated task actions as frontier members, this sidecar's domain and precedence rule control. Q-82 authorises the scheduler after the typed fleet and keeps scheduler authority out of the first visibility repair. The Q-86 proof gate, hardened by Q-92 after the round-5 finding, adds one planning-only requirement to this existing authority: Stage 3 also introduces a typed unwaived complete-only blocker policy so neither a skipped safety proof nor a waiver-backed `complete` status can satisfy a future bounded-convergence production dependency. It adds the policy capability and synthetic tests, not a bounded-convergence production unit.

THE PROBLEM. Once every active unit is visible and typed, the compatibility pending selector still chooses only one lowest-order pending action and serialises independent ready work. Choosing every nonterminal step naively is also wrong: it can schedule dependencies together, treat `deferred` or `optional` as ready, hide an active task action, or turn a read-only adviser into an executor.

ONE ELIGIBLE-STEP DOMAIN. `ready_frontier` is step-only and computed over Roadmap steps whose status is exactly `not-started` or `next`. For ordinary `blocked_by` edges, a candidate is ready exactly when every target resolves and has status `complete` or `skipped`; `in-progress`, `not-started`, `next`, `optional` and `deferred` blockers do not satisfy that generic dependency. This complete-or-skipped meaning remains unchanged. The frontier contains every ready candidate in Roadmap declaration order, once. Step-scoped plan review (independent of implementation status), in-progress exploration/implementation/work review, task plan review/acceptance/standalone review, and question exploration are explicit active-unit actions outside the pending-step frontier. Increments carry no DAG edge and never enter this domain.

UNWAIVED COMPLETE-ONLY SAFETY GATES. Extend the TOML step schema with an explicit blocker product rather than overloading a slug or changing ordinary `blocked_by`:

```toml
[[step.blocker]]
target = "bounded-convergence-option-b-proof"
policy = "complete-only-unwaived"
```

`BlockerPolicy` is a closed enum whose supported exceptional value is `complete-only-unwaived`; ordinary `blocked_by` remains the complete-or-skipped shorthand and generic W3 remains convergence-or-waiver for ordinary Roadmap completion. The parser and source validator reject an unknown policy, unresolved or self target, and any target duplicated within or across the ordinary and typed forms. Render and both `next` surfaces preserve the target and policy so the exceptional gate is visible rather than silently flattened to a generic blocker.

The scheduler and workflow validator use one proof-readiness predicate. The target must have status exactly `complete`; the workflow reconstruction must show direct round-backed convergence for every target review unit at its declared risk-class bar, which is two consecutive clean rounds for `bounded-convergence-option-b-proof-inc1`; and the target's nested waiver list must contain no step- or increment-unit convergence waiver, whether self-declared or record-backed. The predicate reuses the workflow checker's risk-class and segmented-round reconstruction but deliberately does not take W3's covering-waiver branch. A generic waiver may still make an ordinary step workflow-valid and `complete`; it cannot create proof-derived production readiness.

The status truth table covers all seven current `StepStatus` values: only `complete` can proceed to the round-and-waiver checks, while `not-started`, `in-progress`, `skipped`, `next`, `optional`, and `deferred` are blocked. Derive the cases from the exhaustive status inventory so a new status cannot inherit an accidental answer. A second table spans both waiver units and every legal reason/evidence-tier pairing: self-declared `predates-logging` and `review-skipped`, and record-backed `accepted-at-escalation`, each at step and increment scope. Each fixture gives the proof status `complete`; record-backed fixtures carry a valid decision-scoped escalation; every one must remain blocked. Separate roundless and below-streak `complete` fixtures prove that absence of a waiver does not substitute for round-backed risky convergence.

Workflow validation rejects an `in-progress` or `complete` dependent whenever its unwaived complete-only target fails any part of that same predicate, closing manual status-advance and waiver-backed bypasses. A `skipped` dependent performs no production work and needs no such progression error; it remains terminally non-delivering.

Every future bounded-convergence production step must use that exact typed edge to `bounded-convergence-option-b-proof`; ordinary `blocked_by = ["bounded-convergence-option-b-proof"]` is invalid for that safety contract because a skipped or waiver-completed proof could satisfy it. If typed support is absent, such a production step cannot be authored as ready or valid. This step adds no production implementation unit and makes no current step depend on the proof.

TASK/ACTION PRECEDENCE AND SERIAL FALLBACK. The typed fleet first exposes explicit active units in their declared order. If one has an actionable instruction, `selected_action` remains the first such active-unit action; task acceptance/plan review, Roadmap plan review, question exploration, or an active delivery-step action therefore keeps focus even when independent pending steps appear in `ready_frontier`. The scheduler still reports those pending candidates as advisory parallel opportunities, but it does not replace the active instruction. Only when no explicit active unit is actionable does `selected_action` become the first `ready_frontier` member, replacing `workflow-loop-visibility`'s one-step pending fallback. Consequently the selected-action membership invariant is conditional: a frontier-selected action must be a byte-for-byte member of `ready_frontier`; an explicit active-unit selection is a member of `active_units` and need not appear in the frontier.

Project the frontier and selection origin on JSON and human surfaces. Human output names the one serial action separately from the remaining advisory parallel candidates. The tool never spawns, reserves, leases, mutates or merges work; the orchestrator decides whether its isolation budget permits any proposed fan-out.

No increment-level DAG, resource allocator, priority score, daemon, persisted lease, automatic merge, or bounded-convergence production unit enters this step. The plan's step graph is the only scheduling graph.

### Increment 1, `workflow-ready-frontier-scheduler-inc1`

RISK CLASS `risky` (two consecutive clean review rounds). Agents act on scheduler advice, so an invalid frontier can start work before its dependency or fan out conflicting authority. The function is pure and read-only, which makes exhaustive fixture testing possible but does not reduce the consequence of wrong advice.

ACCEPTANCE.

1. One table-driven eligibility suite covers independent ready steps, a dependency chain, a diamond, unresolved blockers, blockers in every Roadmap status, terminal candidate steps, and no-ready-work. It proves the only candidate statuses are `not-started` and `next`, and every frontier is declaration ordered and duplicate-free.
2. For an ordinary `blocked_by` edge, a `complete` blocker and a `skipped` blocker both satisfy the dependency. Red mutations that require strict `complete`, accept `optional`/`deferred`, or treat scheduled/in-progress blockers as satisfied fail focused fixtures.
3. For a typed `complete-only-unwaived` edge to `bounded-convergence-option-b-proof`, readiness requires all of exact `complete` status, round-backed convergence at the declared risky bar, and no target step or increment convergence waiver. Red status controls set the proof in turn to `not-started`, `in-progress`, `skipped`, `next`, `optional`, and `deferred` and require the synthetic production candidate to remain absent from the frontier. The `skipped` case kills any reuse of the ordinary predicate. A status-inventory drift control fails when a new `StepStatus` lacks an expectation. Red waiver controls hold the proof at `complete` and cover self-declared and record-backed waivers at both step and increment scope, including every legal reason/evidence-tier pairing and valid escalation evidence; all remain blocked. Roundless and one-clean-round risky targets also remain blocked. Source validation rejects unknown, dangling, self, or duplicate typed blockers; workflow validation rejects an in-progress or complete dependent whenever the same status, round, or waiver predicate fails. The ordinary skipped-blocker and generic convergence-waiver fixtures remain green beside these controls.
4. The frontier is maximal over that one domain: returning only the first ready step fails an independent/diamond fixture, and returning every nonterminal step fails dependency and status fixtures.
5. Explicit active-unit precedence is pinned. A task-scoped acceptance plus independent pending work selects acceptance while reporting the pending frontier beside it; an active work-review plus independent pending work selects the review; a question-scoped exploration behaves the same. None is coerced into a frontier member or rewritten as a generic worker action.
6. When no explicit active unit is actionable, `selected_action` is the first frontier member byte-for-byte after JSON decoding and the remaining members are parallel candidates. Human output identifies this as the serial fallback. A one-ready-step fixture produces the same planner action as the pre-scheduler pending fallback.
7. Membership is conditional and tested on both branches: a frontier-origin selection absent from `ready_frontier` fails; an active-unit-origin selection absent from `active_units` fails; task acceptance with a non-empty frontier is valid and must not be rejected by the frontier-membership guard.
8. Active review, ordinary skipped-blocker, unwaived-complete-only-proof-blocker, task-acceptance-with-pending-work and serial-fallback fixtures are golden on both human and JSON surfaces. The typed blocker target, policy, round-backed state, and waiver-free result remain visible. Existing visibility/typed-fleet phase actions and declared risk-class output stay unchanged.
9. Determinism holds across runs and machines. No wall clock, filesystem lock, model capacity or worktree availability changes the pure frontier.
10. No command writes the plan, metrics, ledger or worktree; no spawn/merge API or bounded-convergence production unit is added. Red path review rejects `driver/record.rs`, a daemon or an increment-level scheduler.
11. README documents advisory frontier semantics, active-action precedence, ordinary skipped blockers, unwaived complete-only proof blockers, and serial fallback; the canonical architecture summary points to this focused authority; `CHANGELOG.md` records the new output. Pack guidance changes only if it currently implies exactly one ready step may exist.
12. Both validation modes, strict render, tests including red mutations, Clippy, diff checks and ASCII checks pass.
