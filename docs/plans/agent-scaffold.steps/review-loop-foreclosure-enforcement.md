### `review-loop-foreclosure-enforcement`: report and enforce review-loop foreclosure and the total-round cap

Decision `Q-78-foreclosure-enforcement` chose `Report and enforce foreclosure plus the round cap`, over report-only and keeping both advisory. The choice already exists in the event log; this step gives it focused Roadmap ownership after the structured class, TOML-waiver guidance and rebuild-boundary rules land.

THE PROBLEM. `WorkflowSpec` carries `round_cap`, and `next` reports escalation only after a loop reaches it. `validate --workflow` does not enforce the cap. More sharply, a convergence loop can become unable to reach its required consecutive-clean streak before the cap: with rounds used `r`, current clean streak `c`, cap `k` and required streak `q`, foreclosure holds when `k - r < q - c`. Running another review in that state spends a round without any possible converging outcome.

THE SHARED RECONSTRUCTION. Extract one ordered loop-window reconstruction used by `validate --workflow` and `next`. Round and escalation records retain their one-based JSONL record ordinal. A scoped escalation is a segment boundary: later rounds for that exact unit start a new counter window, while prior rounds remain history. The loop identity is structured: a Roadmap work loop uses its resolved step/increment and `work_review`; a task-level plan-review loop uses its registered task plus `plan_review`. Acceptance and standalone review are single-pass phases and never get folded into a convergence-loop cap window merely because they share a task string. Within the active window, compute rounds used, current clean streak, required streak, cap and foreclosure from the structured records and `WorkflowSpec`. Risk-class inconsistency is checked first; convergence is then checked before foreclosure and cap, preserving the existing convergence-first precedence.

ENFORCEMENT BOUNDARY. `next` reports `escalate` as soon as the active enforced window is foreclosed or reaches the cap without convergence, with a reason that distinguishes the two. `validate --workflow` rejects a foreclosed active window with no following scoped escalation, a cap-reached unconverged window with no following scoped escalation, and any enforced segment containing more rounds than the cap. A joined escalation closes that violation and resets the next segment. Historical rounds before a real escalation remain history and never count against its following segment.

Record 383 describes a second escalation and record 384 describes a human-directed rebuild, but prose inside a round is not a `type:"escalation"` event and cannot segment ordered reconstruction. The task has no Roadmap step. Acceptance records 432 and 433 are later single-pass phases, not an eighth/ninth plan-review round. Reproduce the defect by selecting `task == "q78-design-pass" && type == "round" && phase == "plan_review"` in record order and separately selecting an escalation for the same task; the first selection yields records 380-386 and the second is empty.

Adopt cap enforcement honestly with an optional typed `[[meta.review_cap_adoption]]` boundary in the TOML source, not with a fabricated event or a rewritten log. Its only live shape in this increment is a task-scoped convergence-loop boundary carrying `task`, `phase = "plan_review"`, `through_record`, `through_record_sha256` and the closed reason `predates-cap-enforcement`. This increment adds exactly one such entry to the current plan: `task = "q78-design-pass"`, `through_record = 386`, and SHA-256 `4e7aed64e77ca228347de1cfbcf620ca2d6b6f3d8550b606212b3b448d0e95c6` over record 386's raw JSON bytes without its line ending. The task must resolve to `[meta].title` or `[meta].orphan_tasks`; the ordinal must name a matching round of the declared phase; the digest must match; duplicates and a boundary that points through a future/nonmatching record fail closed. The boundary retires that one pre-adoption window for cap/foreclosure enforcement only and starts a fresh enforced window for any later matching round. It is not an escalation, does not claim the historical counters reset when they did, and does not exempt W3, risk-class consistency or any post-boundary round.

A fresh TOML plan omits `[[meta.review_cap_adoption]]`, so cap/foreclosure enforcement starts at its first convergence-loop round. The current entry is a migration fact about one evidenced legacy segment, not a general escape hatch; adding or moving one requires a plan/reviewed migration with a reproduced pre-adoption segment and pinned record digest. This preserves fail-loud enforcement for future Roadmap and non-Roadmap loops while letting current append-only history remain intact.
