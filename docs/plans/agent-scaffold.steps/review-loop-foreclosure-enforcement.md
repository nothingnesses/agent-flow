### `review-loop-foreclosure-enforcement`: report and enforce review-loop foreclosure and the total-round cap

Decision `Q-78-foreclosure-enforcement` chose `Report and enforce foreclosure plus the round cap`, over report-only and keeping both advisory. The choice already exists in the event log; this step gives it focused Roadmap ownership after the structured class/selection, TOML-waiver guidance and rebuild-boundary rules land.

THE PROBLEM. `WorkflowSpec` carries `round_cap`, and `next` reports escalation only after a loop reaches it. `validate --workflow` does not enforce the cap. More sharply, a convergence loop can become unable to reach its required consecutive-clean streak before the cap: with rounds used `r`, current clean streak `c`, cap `k` and required streak `q`, foreclosure holds when `k - r < q - c`. Running another review in that state spends a round without any possible converging outcome.

THE SHARED RECONSTRUCTION. Extract one ordered loop-window reconstruction used by `validate --workflow` and `next`. Round and escalation records retain their one-based JSONL record ordinal. A scoped escalation is a segment boundary: later rounds for that exact unit start a new counter window, while prior rounds remain history. The loop identity is structured and phase-bearing. A recorded Roadmap work window uses each event's resolved step, exact increment and `work_review`; the selected active-work `(step, increment)` supplies the same identity before round one and must agree once records exist. A task-level convergence window uses its exact registered task and `plan_review`, with an active task row supplying the pre-round identity. Acceptance and standalone review are single-pass phases and never get folded into a convergence-loop cap window merely because they share a task string.

Every convergence identity reads the authoritative class from the declaration substrate delivered by `structured-risk-class-source`: a Roadmap loop resolves its `[[step.increment]]`, and a task plan-review loop resolves the unique `[[task_loop]]` row keyed by `(task, plan_review)`. The reconstruction requires every snapshot to match, then computes rounds used, current clean streak, required streak, cap and foreclosure from that declaration, the ordered events and `WorkflowSpec`. A recorded window with a missing declaration or mismatch, and an asserted active window with a missing/unresolved selection, is checked before any convergence arithmetic; convergence is then checked before foreclosure and cap, preserving the existing convergence-first precedence. Retired historical windows need no active-work row. Acceptance and standalone review carry event snapshots but no declared class, streak target, foreclosure or cap segment.

ENFORCEMENT BOUNDARY. `next` reports `escalate` as soon as the selected active enforced window is foreclosed or reaches the cap without convergence, with a reason that distinguishes the two. `validate --workflow` rejects a foreclosed active window with no following scoped escalation, a cap-reached unconverged window with no following scoped escalation, and any enforced segment containing more rounds than the cap. A joined escalation closes that violation and resets the next segment. Historical rounds before a real escalation remain history and never count against its following segment.

Record 383 describes a second escalation and record 384 describes a human-directed rebuild, but prose inside a round is not a `type:"escalation"` event and cannot segment ordered reconstruction. The task has no Roadmap step and is registered in `[meta].orphan_tasks`; under the declaration model it also carries one exact `[[task_loop]]` row with `phase = "plan_review"` and `risk_class = "risky"`. Acceptance records 432 and 433 are later single-pass phases, not an eighth/ninth plan-review round and do not read that declaration. Reproduce the defect by selecting `task == "q78-design-pass" && type == "round" && phase == "plan_review"` in record order and separately selecting an escalation for the same task; the first selection yields records 380-386 and the second is empty.

Adopt cap enforcement honestly with an optional typed `[[meta.review_cap_adoption]]` boundary in the TOML source, not with a fabricated event or a rewritten log. Its only live shape in this increment is a task-scoped convergence-loop boundary carrying `task`, `phase = "plan_review"`, `through_record`, `through_record_sha256` and the closed reason `predates-cap-enforcement`. This increment adds exactly one such entry to the current plan: `task = "q78-design-pass"`, `through_record = 386`, and SHA-256 `4e7aed64e77ca228347de1cfbcf620ca2d6b6f3d8550b606212b3b448d0e95c6` over record 386's raw JSON bytes without its line ending. The task must resolve to `[meta].title` or `[meta].orphan_tasks`, the matching `[[task_loop]]` declaration must exist with the same phase, the ordinal must name a matching round, and the digest must match; duplicates and a boundary that points through a future/nonmatching record fail closed. The boundary retires that one pre-adoption window for cap/foreclosure enforcement only and starts a fresh enforced window for any later matching round. It is not an escalation, does not claim the historical counters reset when they did, and does not exempt declaration/snapshot agreement or any post-boundary round.

A fresh TOML plan omits `[[meta.review_cap_adoption]]`, so cap/foreclosure enforcement starts at its first convergence-loop round. The current entry is a migration fact about one evidenced legacy segment, not a general escape hatch; adding or moving one requires a plan/reviewed migration with a reproduced pre-adoption segment and pinned record digest. This preserves fail-loud enforcement for future Roadmap and task loops while letting current append-only history remain intact.
