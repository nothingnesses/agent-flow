### `workflow-loop-visibility`: give `next` a legal typed phase carrier and project every active unit while selecting one action (`Q-82`)

Q-82 chose `Schedule visibility and scheduling in stages`. This step is the first stage only: repair phase correctness and visibility. It gives `next` no authority to schedule parallel work and does not build the Stage-2 typed fleet. It follows `structured-risk-class-source` so every review-shaped projection reads the declared increment class rather than reintroducing first-round authority.

THE PROBLEM. Stage 1 deliberately selects one lowest-order `in-progress` step and models it as a review loop. At the Q-82 intake, a run therefore presented an exploration as `awaiting-first-review`, hid other active work and surrounded one selected block with roughly 728 KB of output (the exact historical measurement has one source in `docs/plans/code-value-audit.explorations/Q-58-ablation-design.md`). Status alone cannot distinguish exploration, implementation and work review, while a step-only phase field cannot represent plan review, acceptance or an exploration that deliberately precedes any Roadmap step. Replacing the old selector wholesale would also erase its legal `ready-to-plan` and `blocked` advice for a fresh or dependency-blocked plan.

THE STRUCTURED CARRIER. Add an ordered `[[active_work]]` array to the TOML plan source and parse each row at the boundary as an internally tagged union, not as a phase string plus optional fields:

- `scope = "task"` carries `task` plus one of `plan_review`, `acceptance` or `review`. The task id must equal `[meta].title` or resolve through the plan's declared orphan-task registry. It carries no `step` or `question` and is independent of every implementation step's Roadmap status.
- `scope = "question"` carries a resolving `question` id plus `exploration`. The question must have status `exploring`; the row carries no `task` or `step` and is independent of every Roadmap status. This is the legal carrier for Q-68/Q-69-shaped design passes whose implementation step does not exist yet.
- `scope = "step"` carries a resolving Roadmap `step` plus one of `exploration`, `implementation` or `work_review`. The referenced step must be `in-progress`. It carries no `task` or `question`.

Serde/source types use separate task-, question- and step-phase variants under `ActiveWork::{Task, Question, Step}`, with unknown fields denied. Validation rejects every cross-product error, an unresolved identity, a duplicate active-unit identity, a question that is not `exploring`, and a step row whose Roadmap step is not `in-progress`. A task plan review or acceptance is never represented by changing an implementation status, and a question-scoped exploration is never represented by borrowing an unrelated step.

AUTHORITY AND LEGAL TRANSITIONS. The orchestrator is the sole actor authorised to advance `[[active_work]]`, as integration-level workflow state after role output and checkpoint evidence are durable; planners, implementers, reviewers, triagers and explorers do not self-advance it. Update the canonical authority list and orchestrator prompt with that one operation rather than leaving an unowned mutable field. The allowed graph is explicit: task `plan_review` remains while plan fixes/reviews repeat and retires on convergence; question `exploration` retires after its design result is durable and the question moves to `open`; step `exploration` retires after its result and human decision are durably folded; step `implementation -> work_review`, `work_review -> implementation` on valid findings, and `work_review -> retired` when convergence permits the orchestrator's separate status-complete operation; task `acceptance -> retired` on acceptance or routes to task `plan_review` / step `implementation` for a valid shortfall before a later fresh acceptance; task `review` is a single reviewers-then-triager pass and then retires. Opening an entry, changing its phase, retiring it and reordering active entries are orchestrator operations recorded in the same commit as the boundary they reflect. The tool remains read-only.

THE PROJECTION AND COMPATIBILITY FALLBACK. `next` maps every explicit carrier row to one phase-correct typed `active_units` entry in declaration order. Task review phases reconstruct task-scoped state without borrowing a Roadmap status; question and step exploration emit explorer actions without review arithmetic; implementation emits its implementer action; work review joins the shared round evidence and the declared increment class. `selected_action` is copied byte-for-byte from the first actionable explicit unit. The legacy singular `active_loop` remains during the compatibility window as an alias of that selected unit only when it is a review loop; it is never reconstructed separately.

An absent or empty explicit carrier remains legal. Until Stage 3 replaces it, `next` retains the current pending-step fallback only for the two legal pending states: choose the lowest-order `not-started`/`next` step whose blockers are satisfied as typed `ready-to-plan`, else the lowest-order pending step as typed `blocked`. The fallback is inserted into the same projected `active_units`/`selected_action` model with an origin that distinguishes it from an authored carrier row, and appears identically on human and JSON surfaces. It never infers an `in-progress` review loop, so it cannot recreate the motivating phase bug. An empty carrier with legal pending work therefore cannot mean "no action"; an empty carrier with only unrepresented in-progress work reports a typed missing-active-work reason instead of guessing.

Declaration order supplies deterministic one-action focus only, not permission to spawn every visible unit. `workflow-ready-frontier-scheduler` later replaces the pending fallback with its ready frontier while preserving explicit active-unit precedence.

### Increment 1, `workflow-loop-visibility-inc1`

RISK CLASS `risky` (two consecutive clean review rounds). The increment changes the plan schema and the machine output agents act on, and a phase error can dispatch the wrong authority. It is read-only and introduces no scheduler, which bounds the risk without making it low.

ACCEPTANCE.

1. Source parsing accepts the three legal union arms and rejects every cross-product error: task phase plus step/question identity, question exploration plus task/step identity, step phase plus task/question identity, missing or extra identity, unknown phase, unresolved identity, duplicate unit, non-`exploring` question and a step row whose Roadmap step is not `in-progress`. Each error names the row and illegal combination. A fresh template with no explicit `[[active_work]]` remains valid.
2. Every phase appears exactly once on JSON and human surfaces. Red fixtures put task phases on an implementation step and put a question exploration on a fake unrelated step; both fail before `next` runs.
3. Task review rows emit phase-correct reviewer/triager actions; both exploration variants emit explorer actions; implementation emits the implementer action; work review emits its reconstructed review action and declared increment risk class. Neither exploration variant carries a review streak or false `awaiting-first-review`. A red mutation routing every row through step-review reconstruction fails all non-work-review fixtures.
4. Transition-table tests cover every legal edge and representative illegal edges. They prove only the orchestrator operation advances the carrier, a question exploration can retire without any Roadmap status edit, and advancing another carrier does not mutate status. Current-plan backfill, if any work is active when this increment lands, uses cited durable evidence and changes no unrelated status.
5. A mixed fixture projects every explicit carrier row once as `active_units` in declaration order. `selected_action` equals the first actionable member byte-for-byte after JSON decoding, and compatibility `active_loop`, when present, equals the selected review unit. 6. Empty-carrier fixtures pin the retained fallback on both surfaces: a fresh one-step plan emits typed `ready-to-plan`, role `planner` and `start-plan`; a dependency-blocked pending step emits typed `blocked` with its blockers and resolve-blockers action.
