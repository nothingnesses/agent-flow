### `workflow-loop-visibility`: give `next` a legal typed phase carrier and project every active unit while selecting one action (`Q-82`)

Q-82 chose `Schedule visibility and scheduling in stages`. This step is the first stage only: repair phase correctness and visibility. It gives `next` no authority to schedule parallel work and does not build the Stage-2 typed fleet.

THE PROBLEM. Stage 1 deliberately selects one lowest-order `in-progress` step and models it as a review loop. At the Q-82 intake, a run therefore presented an exploration as `awaiting-first-review`, hid other active work and surrounded one selected block with roughly 728 KB of output (the exact historical measurement has one source in `docs/plans/code-value-audit.explorations/Q-58-ablation-design.md`). Status alone cannot distinguish exploration, implementation and work review, while a step-only phase field cannot represent plan review or acceptance from their legal task-level states. A different sort or a fake `in-progress` implementation step cannot repair either defect.

THE STRUCTURED CARRIER. Add an ordered `[[active_work]]` array to the TOML plan source and parse each row at the boundary as an internally tagged union, not as a phase string plus optional fields:

- `scope = "task"` carries `task` plus one of `plan_review`, `acceptance` or `review`. The task id must equal `[meta].title` or resolve through the plan's declared orphan-task registry. It carries no `step` and is independent of every implementation step's Roadmap status.
- `scope = "step"` carries a resolving Roadmap `step` plus one of `exploration`, `implementation` or `work_review`. The referenced step must be `in-progress`. It carries no `task`.

Serde/source types use separate task-phase and step-phase enums under `ActiveWork::{Task, Step}`, with unknown fields denied. Validation rejects a task phase on a step row, a step phase on a task row, a missing or extra identity, an unresolved identity and duplicate active-unit identities. A task-level plan review or acceptance is never represented by changing an implementation step's status. An absent array means no explicitly active work, so a fresh starter plan remains valid.

AUTHORITY AND LEGAL TRANSITIONS. The orchestrator is the sole actor authorised to advance `[[active_work]]`, as integration-level workflow state after the role output and checkpoint evidence are durable; planners, implementers, reviewers and triagers do not self-advance it. Update the canonical authority list and orchestrator prompt with that one operation rather than leaving an unowned mutable field. The allowed graph is explicit: task `plan_review` remains while plan fixes/reviews repeat and retires on convergence; step `exploration` retires after its result and human decision are durably folded; step `implementation -> work_review`, `work_review -> implementation` on valid findings, and `work_review -> retired` when convergence permits the orchestrator's separate status-complete operation; task `acceptance -> retired` on acceptance or routes to task `plan_review` / step `implementation` for a valid shortfall before a later fresh acceptance; task `review` is a single reviewers-then-triager pass and then retires. Opening an entry, changing its phase, retiring it and reordering active entries are all orchestrator operations recorded in the same commit as the durable boundary they reflect. Validation rejects direct phase edges outside this graph when a before/after transition is supplied to the transition test; the tool remains read-only and does not write the carrier.

THE PROJECTION. `next` maps every carrier row to one phase-correct typed `active_units` entry in carrier declaration order. Task plan review, acceptance and standalone review reconstruct their task-scoped review state without borrowing a Roadmap status; step work review joins the shared round evidence for its step/increment; exploration and implementation emit their own actor/action without entering review arithmetic. When at least one unit is active, `selected_action` is copied byte-for-byte from the first actionable `active_units` entry in declaration order. With no active unit it is absent with a typed reason. The legacy singular `active_loop` remains during the compatibility window as an alias of the selected unit when that unit is a review loop; it is never reconstructed separately. Declaration order supplies deterministic one-action focus only, not permission to spawn every visible unit; Stage 3 later computes a ready frontier.

### Increment 1, `workflow-loop-visibility-inc1`

RISK CLASS `risky` (two consecutive clean review rounds). The increment changes the plan schema and the machine output agents act on, and a phase error can dispatch the wrong authority. It is read-only and introduces no scheduler, which bounds the risk without making it low.

ACCEPTANCE.

1. Source parsing/validation accepts the two legal union arms and rejects every cross-product error: task phase plus step identity, step phase plus task identity, missing identity, unknown phase, unresolved identity, duplicate unit and a step-scoped row whose Roadmap step is not `in-progress`. Each error names the row identity and illegal combination. A fresh template with no `[[active_work]]` remains valid.
2. Separate fixtures construct `plan_review`, `acceptance` and standalone `review` as task-scoped units without changing an implementation status, and `exploration`, `implementation` and `work_review` as step-scoped units on legal `in-progress` steps. Every phase appears exactly once on JSON and human surfaces. Red fixtures that put plan review or acceptance on an implementation step fail source parsing before `next` runs.
3. The task plan-review, acceptance and review rows emit their phase-correct reviewer/triager action; exploration emits the explorer action; implementation emits the implementer action; work review emits its reconstructed review action. Exploration and implementation carry no review streak or false `awaiting-first-review`. A red mutation routing every row through step-review reconstruction fails all non-work-review phase fixtures.
4. Transition-table tests cover every legal edge and representative illegal edges. They also prove only the orchestrator operation advances the carrier and that advancing the carrier does not mutate a Roadmap status. The current plan's active entries are backfilled from cited durable evidence during this increment with no existing status change.
5. A mixed fixture projects every carrier row once as `active_units` in declaration order. `selected_action` equals the first actionable member byte-for-byte after JSON decoding, and the compatibility `active_loop`, when present, equals the selected review unit rather than a separately derived answer. Reordering the carrier changes selection deterministically but never grants spawn authority.
6. Existing Stage-1 review-state fixtures keep their state, streak, cap, transitions and output through the compatibility alias. JSON documents the new `active_units` / `selected_action` vocabulary; human output labels the selected row.
7. Output size is freshly measured on the motivating plan. The result reports the contribution of active-unit visibility separately from the Q-58 resume carrier and does not claim this step solves carrier bloat.
8. No `src/driver/` fleet, DAG scheduler, write command, worktree spawn or parallel execution enters this increment. A changed-path review rejects those scopes.
9. README documents the typed active-unit union, plural projection, selected action and compatibility alias. Pack plan guidance/templates and their committed copies document `[[active_work]]`; canonical AGENTS/orchestrator guidance names the orchestrator as its advancing actor and states the transition boundary. `CHANGELOG.md` records the schema/output addition.
10. Both validation modes, strict render, tests including red controls, Clippy, diff checks and ASCII checks pass.
