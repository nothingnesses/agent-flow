### `workflow-loop-visibility`: extend the typed phase carrier and project every active unit while selecting one action (`Q-82`)

Q-82 chose `Schedule visibility and scheduling in stages`. This step is the first visibility stage only: repair phase correctness and plural visibility. It gives `next` no authority to schedule parallel work and does not build the Stage-2 typed fleet. It follows `structured-risk-class-source`, which now owns the two convergence-bearing `[[active_work]]` variants because a task `plan_review` and a Roadmap `work_review` need an authoritative declaration and exact open-loop identity before round one. This step extends that carrier rather than replacing its task/phase or step/increment selector.

THE PROBLEM. Stage 1 deliberately selects one lowest-order `in-progress` step and models it as a review loop. At the Q-82 intake, a run therefore presented an exploration as `awaiting-first-review`, hid other active work and surrounded one selected block with roughly 728 KB of output (the exact historical measurement has one source in `docs/plans/code-value-audit.explorations/Q-58-ablation-design.md`). Status alone cannot distinguish exploration, implementation and work review, while a step-only phase field cannot represent plan review, acceptance or an exploration that deliberately precedes any Roadmap step. Replacing the old selector wholesale would also erase its legal `ready-to-plan` and `blocked` advice for a fresh or dependency-blocked plan.

THE STRUCTURED CARRIER. Extend the ordered `[[active_work]]` array in the TOML plan source and keep each row parsed at the boundary as an internally tagged union, not as a phase string plus optional fields:

- `scope = "task"` carries `task` plus one of `plan_review`, `acceptance` or `review`. The task id must equal `[meta].title` or resolve through the plan's declared orphan-task registry. A `plan_review` row must resolve the exact `(task, plan_review)` `[[task_loop]]` declaration established by `structured-risk-class-source`; `acceptance` and `review` are single-pass rows and must not borrow that convergence class. Task rows carry no `step`, `question` or `increment` and are independent of every implementation step's Roadmap status.
- `scope = "question"` carries a resolving `question` id plus `exploration`. The question must have status `exploring`; the row carries no `task`, `step` or `increment` and is independent of every Roadmap status. This is the legal carrier for Q-68/Q-69-shaped design passes whose implementation step does not exist yet.
- `scope = "step"` carries a resolving Roadmap `step`, a resolving `increment` owned by that step, plus one of `exploration`, `implementation` or `work_review`. The referenced step must be `in-progress`. The `(step, increment)` pair is the one durable open-increment selection introduced by `structured-risk-class-source`: it persists across `implementation -> work_review`, and `work_review` reads that exact declaration before any round. The row carries no `task` or `question`.

Serde/source types use separate task-, question- and step-phase variants under `ActiveWork::{Task, Question, Step}`, with phase-specific payload structs so required/forbidden fields are represented by type rather than optional cross-products. Validation rejects every cross-product error, an unresolved identity, a duplicate active-unit identity, a question that is not `exploring`, a task plan review with no task-loop declaration, an increment not owned by its step, and a step row whose Roadmap step is not `in-progress`. A task plan review or acceptance is never represented by changing an implementation status, a question-scoped exploration is never represented by borrowing an unrelated step, and no consumer guesses an open increment from declaration order or round recency.

AUTHORITY AND LEGAL TRANSITIONS. The orchestrator is the sole actor authorised to advance `[[active_work]]`, as integration-level workflow state after role output and checkpoint evidence are durable; planners, implementers, reviewers, triagers and explorers do not self-advance it. Update the canonical authority list and orchestrator prompt with that one operation rather than leaving an unowned mutable field. The allowed graph is explicit: task `plan_review` remains while plan fixes/reviews repeat and retires on convergence; question `exploration` retires after its design result is durable and the question moves to `open`; step `exploration` retires after its result and human decision are durably folded; step `implementation -> work_review` retains the exact `(step, increment)`, `work_review -> implementation` on valid findings retains it, and `work_review -> retired` when convergence permits the orchestrator's separate status-complete operation; task `acceptance -> retired` on acceptance or routes to task `plan_review` / the exact step `implementation` unit for a valid shortfall before a later fresh acceptance; task `review` is a single reviewers-then-triager pass and then retires. Opening an entry, changing its phase, retiring it and reordering active entries are orchestrator operations recorded in the same commit as the boundary they reflect. The tool remains read-only.

THE PROJECTION AND COMPATIBILITY FALLBACK. `next` maps every explicit carrier row to one phase-correct typed `active_units` entry in declaration order. Task `plan_review` reconstructs task-scoped convergence state from its task-loop declaration; task single passes carry no streak; question and step exploration emit explorer actions without review arithmetic; implementation emits its implementer action while retaining the chosen increment; work review joins the shared round evidence and the selected increment declaration. `selected_action` is copied byte-for-byte from the first actionable explicit unit. The legacy singular `active_loop` remains during the compatibility window as an alias of that selected unit only when it is a convergence review loop; it is never reconstructed separately.

An absent or empty explicit carrier remains legal. Until Stage 3 replaces it, `next` retains the current pending-step fallback only for the two legal pending states: choose the lowest-order `not-started`/`next` step whose blockers are satisfied as typed `ready-to-plan`, else the lowest-order pending step as typed `blocked`. The fallback is inserted into the same projected `active_units`/`selected_action` model with an origin that distinguishes it from an authored carrier row, and appears identically on human and JSON surfaces. It never infers an `in-progress` review loop or an increment, so it cannot recreate either the motivating phase bug or the declaration-order/latest-round guess. An empty carrier with legal pending work therefore cannot mean "no action"; an empty carrier with only unrepresented in-progress work reports a typed missing-active-work reason.

Declaration order supplies deterministic one-action focus only, not permission to spawn every visible unit. `workflow-driver-typed-fleet` consumes all units and the exact task/step loop identities without a second selector. `workflow-ready-frontier-scheduler` later replaces only the pending fallback with its ready frontier while preserving explicit active-unit precedence.

### Increment 1, `workflow-loop-visibility-inc1`

RISK CLASS `risky` (two consecutive clean review rounds). The increment changes the plan schema and the machine output agents act on, and a phase or increment-selection error can dispatch the wrong authority or convergence bar. It is read-only and introduces no scheduler, which bounds the risk without making it low.
