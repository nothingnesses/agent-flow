### `workflow-driver`: the staged workflow DRIVER, the forward member of a projection family over the workflow (`Q-51`)

The umbrella carries a delivered foundation and scheduled successors. Its TOML Roadmap record is `in-progress` and declares the unchanged `workflow-driver-stage0a`, `workflow-driver-stage0b` and `workflow-driver-stage1` increments; each declaration is `risky`, every joined round snapshot matches it, and each increment reaches the two-clean-round bar, so Stages 0a, 0b and 1 are complete while the umbrella remains open for later stages. Design shape DECIDED (`Q-51`, human, 2026-07-19): the human chose the FULL DRIVER as the target (over the four round-1 explorers' advisory-MVP-only recommendation), staged so no increment hardens a still-evolving workflow. Design record: `docs/plans/mealy-workflow-driver.explorations/r2-synthesis.md` (the authoritative full-driver design + staged build plan), backed by the four `r2-*.md` lens files (`r2-requirements-scope.md`, `r2-user-flows.md`, `r2-design-space-vision.md`, `r2-architecture-build-path.md`) and the round-1 `synthesis.md`. This is a MAJOR initiative, larger than `structured-skeleton`; under Q-83 each successor's focused Roadmap increment declares its class when its loop opens, before round one.

North star (the projection-family framing). The driver is the FORWARD member of a family of folds over two durable sources: the append-only event log `docs/metrics/workflow.jsonl` and a data-driven control spec `.agents/workflow.toml`. The family: `validate --workflow` is the BACKWARD check (did the past obey the rules), `status` is the SUMMARY, `next` is the FORWARD execution (given the state, what the rules dictate next), and `render` extends the family to prose (it generates the AGENTS.md control fragments from the same spec, so process logic and process prose cannot drift). So the driver is not a new subsystem bolted on; it is the missing forward member of a family whose backward and summary members already ship, and it reuses the W3/W4/W5 reconstruction wholesale (the convergence arithmetic `src/workflow.rs` already runs to CHECK a completed history, run forward to EMIT the next move).

The data-driven-constants spec plus the Rust transition function. `.agents/workflow.toml` is a tool-owned, pack-shipped reference asset (the same for every scaffolded project; `agent-scaffold`'s own repo dogfoods its scaffolded copy) that holds ONLY the deterministic CONTROL CONSTANTS and orderings: the risk-class -> required-clean-streak map, the total-round cap, the backstop severity threshold, the phase/loop sequence, the isolation-tier preference order, the role -> prompt-path map, and the findings/ledger/exploration/report path templates. The transition FUNCTION stays Rust (the streak/cap arithmetic the W3 checker already computes, run forward). The split is deliberate: a workflow VALUE change (a constant, a threshold, an added ordering) is a data edit reviewable like a plan edit; only a genuinely new rule KIND is a code change to the interpreter. This is the answer to "keep it data-driven so the workflow evolves without pouring concrete": the parts that change often are data, the fixed interpreter is small code. Both `validate --workflow` and the driver parse one `WorkflowSpec`, which single-sources today's hardcoded `RiskClass::required_streak` (currently duplicated against AGENTS.md prose). A built-in default (`WorkflowSpec::builtin()` equal to today's constants) covers a project shipping no spec, pinned by a `builtin()`-equals-old-constants assertion so an un-migrated project validates byte-for-byte unchanged.

The control-vs-judgment boundary, enforced by types. The tool owns CONTROL (counting streaks for convergence loops, sequencing phases, scheduling the ready frontier, gating the backstop for both process kinds, resolving the isolation tier, emitting prompts); it CONSUMES agent/human JUDGMENT as typed `Input` variants (a triage verdict `{clean | new_valid}`, a recheck result, a human decision, a commit, an override) and NEVER manufactures a verdict. The typed engine (Stage 2) makes this load-bearing: `step` has no branch that produces an `outcome`, a `risk_class`, or a `human_decision`, and `ReviewProcess::{Convergence, SinglePass}` makes it impossible to give acceptance/review a class, streak, foreclosure, or cap. Getting this wrong in the permissive direction hallucinates decisions or review evidence; in the restrictive direction it straitjackets the agent. This is the primary correctness property.

Terminal authority (ORQ-1, decided) and the other open-requirements resolutions. The driver's END STATE is ADVISORY + validated event-RECORDING, NON-BLOCKING in-loop, with an OPT-IN boundary gate (`validate --workflow --strict` in CI or a pre-commit hook, reusing the existing checks/hook pattern) for hard enforcement at the LANDING boundary. So the loop never deadlocks if the tool is skipped, but the boundary gate catches an unrecorded gap before work lands; this also answers ORQ-2 (gate at the boundary, not per-step, keeping the loop robust, harness-agnostic, least-authority, and respecting Q-24's no-runtime-write-path-dependency stance). ORQ-3 (multi-repo) defaults to single-project (a far-stage YAGNI). ORQ-4 (spec-change ceremony): `workflow.toml` is load-bearing config, so edits go through the normal plan + review like AGENTS.md changes, no new ceremony. ORQ-5 (reminder cadence): light, each `next` surfaces only the reminders relevant to the current action, not a per-call dump that trains agents to ignore it.

Complements, does not subsume. The driver COMPLEMENTS (does not replace) the re-grounding + provenance step and the `Q-50` doc-currency guidance: they address different drift axes (the driver fights CONTROL-drift, an agent forgetting a rule that applies right here; re-grounding fights CONTEXT-drift; Q-50 fights DOC-TRUTH-drift). Q-50 is in fact a PREREQUISITE if the driver emits prompts assembled from the role-prompt files (a driver is only as correct as those files). Those cheaper items un-gate and ship on their own schedule rather than waiting on this.

Staged architecture. The delivered path is 0a -> 0b -> 1. Q-82 now schedules the corrective phase/visibility carrier, Stage 2's typed fleet and Stage 3's read-only scheduler as focused Roadmap successors; the remaining generation, write-path and authoritative-driving work stays behind its evidence gates. Detailed implementation criteria and dependencies live only in those child sidecars.

- Stage 0a (DELIVERED, TOML class `risky`, no deps): the `.agents/workflow.toml` control-constants spec + `WorkflowSpec` + `WorkflowSpec::builtin()`; single-source the convergence constants into the W3 check (replace `RiskClass::required_streak`'s hardcoded `match` with a spec lookup, thread the spec into `w3_problems`, add the round cap as `spec.round_cap()`); add a `--workflow-spec` flag on `validate`. Behaviour-preserving, guarded by the existing W3 tests plus the `builtin()`-equals-old-constants assertion. RISKY because it touches the safety-relevant convergence bar and adds a scaffolded asset every downstream project inherits, but it changes no behaviour. VALUE independent of the driver: closes the live `required_streak`/AGENTS.md duplication (a real bug-closing win) and lays the data-driven-spec foundation the whole driver rests on. Deps: none (builds on the shipped `structured-skeleton` + `validate --workflow`). ACCEPTANCE: `validate --workflow` on the live repo is byte-for-byte unchanged with the built-in default; the `builtin()`-equals-old-constants assertion holds; a spec with an altered `required_streak` changes the enforced bar the checker applies (`round_cap` and the backstop severity ship as spec data in Stage 0a but are not W3-enforced until a later stage, so they do not alter the bar yet).
- Stage 0b (DELIVERED, TOML class `risky`, deps 0a): generate the AGENTS.md control-constant fragment from the spec via a pack `{{workflow_control}}` render slot (the streak-per-class sentence, the cap, the backstop severity, the tier order, the path conventions), byte-compare guarded exactly as the plan's generated status vocabulary already is. This is the PACK generation path (`build_assets` filling the guidance template's slots at scaffold time), not `plan::render`; the hand-authored rationale prose stays around the slot. Proves the code-vs-prose generation closure on the smallest, highest-value content before it is widened. Deps: 0a (the spec). ACCEPTANCE: the generated fragment matches the spec constants; the byte-compare check fails on a hand edit of the generated fragment and on a stale fragment after a spec edit.
- Stage 1 (DELIVERED, TOML class `risky`, deps 0a): the advisory, read-only, stateless `agent-scaffold next` MVP, largely the already-planned `state-queries` step (`Q-28`/`Q-34`) plus a next-action reminder. For the single active review loop it forward-projects the W3 reconstruction to emit the current per-unit state, the valid transitions, and the next action as a filled instruction prompt (the role prompt path from the spec, the artifact and diff range from the ledger's `## RESUME STATE`, the findings/ledger paths from the spec templates, and the phase-keyed Principle reminders), in both JSON and human text. No typed fleet, no scheduler, no write-path. Stateless: recompute from the durable files each call (no `.fsm-state` store), so it survives a crash or compaction. The design-pass estimate was LOW_RISK because the command is read-only, but the loop opened and converged under its declared `risky` plan increment and matching round snapshots. Q-83's successor repair makes that declaration authoritative and gives `next` its class before round one. Deps: 0a (reads the spec); coordinate with `state-queries` to avoid duplicating the `status --resume` slice. VALUE: the point-of-action anti-drift reminder that captures most of the drift-reduction value, and the EVIDENCE SOURCE (adherence rate, drift reduction over ~10 step cycles) that gates every later stage. When the next action is an awaiting-human-decision gate, the reminder set includes the human-input-contract reminder (present the options, their trade-offs, a recommendation, and Principle-judged reasoning), folded here from `human-input-gate-reinforce` part (b) (`Q-54`): this is the point-of-action reinforcement for a rule the orchestrator was observed drifting off, so it is the driver's first concrete anti-drift reminder and its own live evidence. ACCEPTANCE: `next` emits the correct next action and filled prompt for a fixture plan + log + ledger; its forward projection of the streak/cap matches the W3 checker's backward computation on the same files; the awaiting-human-decision reminder carries the human-input-contract cue; output is deterministic across machines.
- Stage 2 (SCHEDULED as `workflow-driver-typed-fleet`, TOML class `risky`): the typed `src/driver/` FSM engine. Consume and extend the reviewed ordered review-process reconstruction delivered by `review-loop-foreclosure-enforcement`; do not extract a second declaration lookup, phase/identity selector, process classifier, or streak/cap/reset formula under the driver. Add `driver/fsm.rs` (`ReviewProcess::{Convergence(ReviewLoop), SinglePass(SinglePassReview)}` with total typed transitions, plus nested `TaskMachine`, `QuestionMachine`, and `StepMachine`), `driver/reconstruct.rs` (the full task/question/step active-unit fleet from `PlanToml` + round log + selected Q-58 carrier + spec), and `driver/emit.rs` (filled instruction prompts from typed state). Task and live increment plan reviews read their own phase-bearing declarations while exact-step and Q-81 Roadmap-increment plan history remain bounded non-active reconstructions; acceptance/review have no constructible class/streak/foreclosure/cap but retain high/critical dismissal re-check; question exploration remains Roadmap-independent; and delivery-step units retain explicit increments. The nesting makes "a `complete` step whose work-review loop never converged" unrepresentable by construction, and exhaustive process transitions make an undefined or cross-kind transition unrepresentable. The focused child sidecar remains the detailed implementation authority for load-bearing dependencies, state variants, and executable criteria.
- Stage 3+ (scheduler scheduled; other branches still gated): Q-82 supersedes the former "real parallel multi-unit execution first" evidence gate for the typed fleet and read-only scheduler only and authorises `workflow-ready-frontier-scheduler` after the fleet. That focused sidecar is the Stage-3 implementation authority. Its pure pending-step frontier contains exactly `not-started`/`next` Roadmap steps whose ordinary `blocked_by` targets are `complete` or `skipped` and whose typed unwaived complete-only proof targets are `complete`, directly converged at their declared risk-class bar, and free of step or increment convergence waivers; every explicit task/question/step action, including Roadmap plan review independent of implementation status, remains outside the frontier and takes selected-action precedence, while the first frontier member is the serial fallback only when no explicit active action exists. It neither spawns nor writes. The other Stage 3+ branches keep their prior gates: generation-widening waits on the delivered 0b fragment's correctness/readability and still owes the pluralize-by-count fix to `control_fragment()`; the guarded `record-*` write-path waits on measured advisory adoption and deliberately reopens Q-24 while preserving hand-writable JSONL; the opt-in authoritative boundary waits on a measured-low override rate. The far corner (calibration closure, a `workflow-viz` read consuming the driver's JSON, multi-repo) stays out of scope until its own scale is real.

Scheduled successor ownership (`Q-82`, human, 2026-08-25). The Stage 0a, 0b, and 1 increment identities and convergence records above stay unchanged. The newly authorised work is split into focused Roadmap steps instead of being appended as a mixed increment here: `structured-risk-class-source` first establishes every live phase-bearing declaration/selection variant and all three bounded historical classifications required before enforcement; `workflow-loop-visibility` extends that one legal task/question/step active-work union, adds phase-correct plural projection, and retains typed pending fallback plus one selected action; `workflow-driver-typed-fleet` then implements Stage 2 after the Q-58/Q-59 carrier and `review-loop-foreclosure-enforcement`'s disjoint convergence/single-pass reconstruction exist; `workflow-ready-frontier-scheduler` follows with Stage 3's pure ready-frontier function and is the implementation authority for eligibility and precedence. Their sidecars own implementation criteria, dependencies, and documentation impact and point back here for architecture. Scheduler authority is absent from the visibility step, and the typed fleet is a declared prerequisite of the scheduler.

YAGNI boundary (what NOT to build). No persisted FSM-state store and no stateful `drive` daemon/REPL (recompute statelessly each call). No judgment in the spec or in `step` (verdicts and human decisions are only typed inputs; risk class comes only from the exact selected plan declaration). No general/Turing-complete process DSL (the spec encodes THIS workflow's fixed constants/sequences/paths/tiers; a new rule KIND is code). No increment-level DAG scheduling (the DAG is step-granularity only). No generating the RATIONALE/role/contract/discipline prose (only the control-constant fragments are generated; the WHY stays hand-authored). No performing isolation (the tool emits the resolved tier; the orchestrator isolates). No per-turn polling during active work (a negative token trade; scope to resume, boundary, and decision points). No flipping to authoritative-blocking before the override rate is measured low. And the driver never subsumes the re-grounding step or Q-50.
