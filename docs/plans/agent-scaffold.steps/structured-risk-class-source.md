### `structured-risk-class-source`: make plan declarations the authoritative review-loop risk-class source

Decision `Q-78-risk-class-source` retired the ledger prose duplicate in favour of structured data. Q-83 settled the Roadmap increment arm: the human chose `Make the plan increment authoritative`, over making the first round authoritative or adding an authoritative loop-open event. This repair preserves that decision. It makes phase part of every live loop identity, supplies the corresponding task-plan declaration, and gives exact step-slug plan-review and non-Roadmap work-review history closed typed dispositions; none of those additions asks the human to choose authority again.

THE REPRODUCED DEFECTS. `[[step.increment]].risk_class` is already required and documented as setting an increment's convergence streak, but `PlanToml::step_views` drops increments, W3 reads the first round's class, and `next` reports no class before round one. A scratch TOML declaring `dangerous-inc1` as `risky` plus one clean round that snapshots `low_risk` currently exits zero from `validate --workflow`; the cheaper one-round bar wins over the declared two-round bar. Before the first round, the same declared increment reaches `next` with `risk_class` and `required_streak` null. The retained fieldless histories `round-log-core-incA` and `round-log-core-incB` cannot pass the current lowercase-only increment-id parser, task-level `plan_review` loops such as `q78-design-pass` have no increment in which to declare a class, and a multi-increment step gives `next` no durable fact identifying which declared sibling is open before that sibling has a round.

The committed log adds phase/owner shapes that the earlier two-arm repair omitted. All 99 `plan_review` rounds need an exact home. Sixty-three resolve to eighteen Roadmap identities: exact step-slug identities for `structured-skeleton` and `checks-runner-worktree-name-collision`, three fieldless-increment identities (`decision-folder-currency-fold`, `workflow-enforcement-tier-fold`, and `workflow-enforcement-tier-endproperty-fold`), and the thirteen structured Q-81 increment identities. Eight `work_review` rounds resolve to no Roadmap step at all, at records 1, 47, 48, 164, 173, 177, 178, and 379. THE AUTHORITATIVE DECLARATION PROJECTION. Parse all live convergence declarations into one phase-bearing `LoopDeclaration` enum:

- `RoadmapIncrement { step, increment, phase, risk_class }` uses exact owned `[[step.increment]]` fields. Q-83's `risk_class` remains authoritative, and a new required `phase = "plan_review" | "work_review"` makes the declaration itself phase-bearing before round one. One increment id declares exactly one phase; changing phase requires a new increment identity rather than reinterpreting history. A round or active selection with the other phase is a mismatch, never a second loop silently sharing the class.
- `TaskPlanReview { task, phase = plan_review, risk_class }` uses one top-level `[[task_loop]]` row carrying exactly `task`, `phase`, and `risk_class`. Its key is the exact `(task, phase)` pair, duplicate keys are rejected, and `task` must equal `[meta].title` or resolve through `[meta].orphan_tasks`. `acceptance`, standalone `review`, and `work_review` are rejected in this table.

The declaration exists and is selected before the first reviewer is spawned. Every round joined to a live convergence loop must resolve to exactly one phase-bearing declaration and match its class; a missing declaration, unresolved or ambiguous join, or mismatch fails closed before convergence, foreclosure, or cap arithmetic. `round.risk_class` stays required as an auditable event snapshot, but it never chooses or lowers the threshold. Acceptance and standalone review snapshots never become a convergence declaration. No reader recovers a missing class from the ledger or the first round.

THE PHASE-PRESERVING ROUND MAPPING. Resolution parses phase first, then preserves the event's exact structured identity. A `plan_review` round carrying `step` plus `increment` first matches an exact bounded historical selector, if one exists; the thirteen Q-81 identities therefore reconstruct through their migration-only historical rows, not through the live delivery declarations that use the same owned increment ids with `phase = "work_review"`. Any other structured Roadmap-increment plan review resolves only to an owned increment declared `phase = "plan_review"`. A pre-migration round carrying `step` but no `increment` keeps `task` byte-for-byte as its review identity: if `task` equals an increment owned by that step, it resolves to that Roadmap-increment declaration; if `task` equals the step slug, it must match that step's exact migration-only history row; any other value fails. A fully fieldless pre-migration round may use the existing leading-slug shim only to find a candidate Roadmap owner, after which the same exact-match rules apply. A non-Roadmap `plan_review` resolves only through its exact task declaration. Structured ids win over the shim, no normalization or case-folding occurs, and an identity that could resolve more than one way is an error rather than a precedence guess.

A `work_review` round resolves to a live convergence loop only through an exact owned Roadmap increment declared with `phase = "work_review"`; it cannot enter `[[task_loop]]` or any historical row. A phase-blind grouping by `(step, increment)` is forbidden: the explicit historical/live variant and phase remain in the key through reconstruction, escalation segmentation, W3, `next`, and the later driver. The same lexical `(step, increment)` may appear in a closed, selector-bounded Q-81 plan-review history and a live work-review declaration, but no declaration carries two phases and no event can cross between them.

ESCALATION PHASE. New convergence-loop escalation records carry `phase = "plan_review" | "work_review"` in addition to their exact task/step/increment identity. The metrics schema remains hand-writable and strict about new guidance; no event is fabricated or rewritten.

THE NARROW INCREMENT-ID COMPATIBILITY CONTRACT. Parse a declared increment id into an `IncrementId` type with exactly two accepted forms. `Canonical` is today's lowercase `is_kebab_case_token`. `LegacyFieldlessSuffix` is accepted only when the owning step slug is itself a canonical lowercase slug and the id is the exact byte string `<owner-step-slug>-inc<X>`, where `<X>` is one ASCII uppercase letter. The legacy arm is stored and compared without case-folding or normalization, is globally unique in the same exact-string namespace as canonical ids, and exists solely so fieldless append-only identities such as `round-log-core-incA` and `round-log-core-incB` can be declared and retain their existing joins. It does not widen step slugs, `blocked_by`, `folds`, question ids, task ids, or any other token class. It also does not admit uppercase in the owner/body, a multi-character suffix, a suffix followed by another component, underscores, non-ASCII, or an id whose owner prefix is a different step.

THE OPEN-LOOP OPERATION. A declaration is not an open-loop signal: this plan legitimately predeclares sibling increments and retained declarations. The orchestrator opens a live loop by authoring or selecting the declaration and committing the matching active-work row before round one.
