### `structured-risk-class-source`: make plan declarations the authoritative review-loop risk-class source

Decision `Q-78-risk-class-source` retired the ledger prose duplicate in favour of structured data. Q-83 settled the Roadmap work-review arm: the human chose `Make the plan increment authoritative`, over making the first round authoritative or adding an authoritative loop-open event. This repair preserves that decision and supplies the corresponding typed declaration for task-scoped convergence loops plus the durable operation that selects an open Roadmap increment; neither extension asks the human to choose authority again.

THE REPRODUCED DEFECTS. `[[step.increment]].risk_class` is already required and documented as setting an increment's convergence streak, but `PlanToml::step_views` drops increments, W3 reads the first round's class, and `next` reports no class before round one. A scratch TOML declaring `dangerous-inc1` as `risky` plus one clean round that snapshots `low_risk` currently exits zero from `validate --workflow`; the cheaper one-round bar wins over the declared two-round bar. Before the first round, the same declared increment reaches `next` with `risk_class` and `required_streak` null. Three further live shapes make a simple projection insufficient: the retained fieldless histories `round-log-core-incA` and `round-log-core-incB` cannot pass the current lowercase-only increment-id parser; task-level `plan_review` loops such as `q78-design-pass` have no increment in which to declare a class; and a multi-increment step gives `next` no durable fact identifying which declared sibling is open before that sibling has a round.

THE TWO AUTHORITATIVE DECLARATIONS. A Roadmap `work_review` loop reads Q-83's existing `[[step.increment]].risk_class`. A task-scoped convergence loop reads one new top-level `[[task_loop]]` row carrying exactly `task`, `phase` and `risk_class`. Its key is the exact `(task, phase)` pair, duplicate keys are rejected, `task` must equal `[meta].title` or resolve through `[meta].orphan_tasks`, and `phase` parses through a closed `TaskConvergencePhase` whose only current value is `plan_review`. `acceptance` and standalone `review` are single reviewers-then-triager passes, not convergence loops; neither may be declared as a `[[task_loop]]`, and their event `risk_class` fields remain descriptive snapshots that never select a streak or cap window. Roadmap `work_review` remains increment-scoped and cannot be smuggled into the task table.

Both declaration arms project into one typed `LoopDeclaration` view: `Roadmap { step, increment, risk_class }` or `Task { task, phase, risk_class }`. The declaration is present and fixed before the first reviewer is spawned. Every round joined to a convergence loop must resolve to exactly one declaration and match its class; a missing declaration, unresolved or ambiguous join, or mismatch fails closed before convergence, foreclosure or cap arithmetic. `round.risk_class` stays required as an auditable event snapshot, but it never chooses or lowers the threshold. No reader recovers a missing class from the ledger or the first round.

THE NARROW INCREMENT-ID COMPATIBILITY CONTRACT. Parse a declared increment id into an `IncrementId` type with exactly two accepted forms. `Canonical` is today's lowercase `is_kebab_case_token`. `LegacyFieldlessSuffix` is accepted only when the owning step slug is itself a canonical lowercase slug and the id is the exact byte string `<owner-step-slug>-inc<X>`, where `<X>` is one ASCII uppercase letter. The legacy arm is stored and compared without case-folding or normalization, is globally unique in the same exact-string namespace as canonical ids, and exists solely so fieldless append-only identities such as `round-log-core-incA` and `round-log-core-incB` can be declared and retain their existing joins. It does not widen step slugs, `blocked_by`, `folds`, question ids, task ids or any other token class. It also does not admit uppercase in the owner/body, a multi-character suffix, a suffix followed by another component, underscores, non-ASCII or an id whose owner prefix is a different step. Source validation owns the syntactic variant; workflow validation proves the exact declared id joins the retained fieldless record through the pre-migration shim.

THE OPEN-INCREMENT OPERATION. A declaration is not an open-loop signal: this plan legitimately predeclares several sibling increments. This increment therefore introduces the two convergence-bearing variants of the ordered `[[active_work]]` union: task `plan_review` carries its exact `task`; step `work_review` carries both a resolving `step` and a resolving `increment` owned by that step. The orchestrator opens a loop by authoring or selecting the declaration and committing the matching active-work row before round one. A declaration may have been prepared earlier, but selection freezes its class for the opened loop; predeclared siblings remain closed. `next` and the shared active-loop reconstruction consume that exact selected identity and never guess from declaration order, lexical order, the latest round, or the first unconverged round group; W3 validates all joined Roadmap histories against the same declaration map without needing an active selector. A missing selection for an asserted active review or a row whose increment belongs to another step is a typed data fault. A row may remain selected while its own loop reports `converged` until the orchestrator retires it, but selecting a retired sibling reconstructs that sibling rather than silently jumping to a newer one. `workflow-loop-visibility` later extends this same union with the non-convergence task/question/step phases and plural projection; it does not create a second increment selector. The Stage-2 fleet consumes the same selected pair.

The plan-source projection, workflow check and forward driver use the one declaration/selection view. `src/plan/source.rs` retains each increment's typed exact id, owner and class, parses `[[task_loop]]`, and parses the convergence-bearing active-work variants instead of normalising them away; `src/workflow.rs` uses that view for W3 and the shared reconstruction; `src/next.rs` uses the selected loop for pre-first-round output and rejects conflicting snapshots rather than selecting either value. Existing Roadmap work-review histories are migrated by declaring their exact retained identities and observed classes, including `round-log-core-incA` and `round-log-core-incB`, before enforcement is switched on. Existing task-level convergence histories are migrated with their registered exact task/phase/class, including `q78-design-pass` + `plan_review` + `risky`; an unregistered historical task must first enter the orphan registry. The append-only round log is not rewritten.

The ledger narrative keeps the review evidence a resuming human needs, but points at the plan declaration, selected active-work identity and joined round records rather than restating class or required count. Narrative round/streak history remains until the separately open structured-ledger design settles its own scope; this step removes only the prose duplicate and settles the relationship among the plan declarations, active selection and event snapshots.

### Increment 1, `structured-risk-class-source-inc1`

RISK CLASS `risky` (two consecutive clean review rounds), declared here in the plan before this loop opens. The increment changes the convergence bar every reviewer loop and downstream scaffold follows. A false green can reduce a declared risky loop to the low-risk bar, so the blast radius is wide.

WHAT CHANGES.

- `src/plan/source.rs`, `src/workflow.rs` and `src/next.rs`: add the typed exact increment-id compatibility arm, the `[[task_loop]]` declaration, the convergence-bearing active-work selector, the shared declaration projection and fail-closed consumers.
- The current plan source: when the implementation lands, add missing historical Roadmap declarations with exact ids/classes, task-loop declarations for registered historical convergence loops, and only the active-work rows then justified by live durable state; do not rename an identity, infer activity from declaration order or manufacture history.
- `pack/AGENTS.md` and its committed renders `AGENTS.md` and `.agents/AGENTS.reference.md`: classify once at loop open, declare the class in the correct plan arm before review, select the exact active loop, repeat the class as a snapshot on every round, and remove the instruction to copy class or required count into ledger prose.
- `pack/prompts/orchestrator.md` and `.agents/prompts/orchestrator.md`: at point of action, declare/read the task or increment declaration, author the exact active-work selection, and reject a missing or conflicting declaration instead of deriving from round one or sibling order.
- `pack/LEDGER.template.md` and `.agents/LEDGER.template.md`: point to the selected declaration and joined rounds without an independent class value.
- `pack/instrument.md`: describe `round.risk_class` as the required event snapshot that must equal the declaration for a convergence loop, and distinguish task `plan_review` from single-pass `acceptance`/`review`.
- `pack/plan-template.plan.toml` and the committed `docs/plans/TEMPLATE.plan.toml`: teach canonical increment ids, the bounded legacy compatibility rule for migration, `[[task_loop]]`, and loop selection without marking every predeclared increment active.
- `README.md` and `CHANGELOG.md`: document fail-closed workflow validation, pre-round `next` output, exact-id migration, task-loop authority and the selection operation.

ACCEPTANCE.

1. The plan parser exposes one typed declaration projection for Roadmap `(step, increment, risk_class)` and task `(task, convergence phase, risk_class)` identities. W3, the shared reconstruction and `next` consume that declaration projection; the active reconstruction and `next` additionally consume one typed selected loop. Red mutations that drop either declaration arm or the selected increment fail the workflow and next suites.
2. `round-log-core` can declare exact ids `round-log-core-incA` and `round-log-core-incB`, retain their observed `low_risk` and `risky` classes, and join the five existing fieldless rounds without renamed ids or new log fields. Lowercasing either declaration makes the exact join fail.
3. Token table tests accept canonical lowercase increment ids and only the owner-matching `<step>-inc[A-Z]` compatibility form. They reject uppercase step slugs, uppercase in the increment body, `-incAB`, `-incA-extra`, owner mismatch, underscores and non-ASCII; all unrelated slug/token tests stay byte-equivalent in meaning.
4. A `[[task_loop]]` fixture accepts `[meta].title` + `plan_review` and a registered orphan + `plan_review`, fixes `risk_class` before round one, and rejects an unknown task, duplicate `(task, phase)`, `work_review`, `acceptance` and standalone `review` phases.
5. The live `q78-design-pass` shape is pinned as a registered orphan `task_loop` with phase `plan_review` and class `risky`. Before a round it reports the two-clean-round bar; one `low_risk` snapshot is a named mismatch and cannot buy convergence. The seven historical `risky` snapshots still join exactly, while the separate acceptance records never enter that convergence window.
6. The reproduced Roadmap downgrade remains red: a `risky` `dangerous-inc1` declaration plus one `low_risk` clean round fails `validate --workflow`, identifies both values and the increment, and never reports convergence. Mutating the round to `risky` leaves one clean round short of the two-round bar.
7. A multi-increment fixture has a converged selected `low_risk` sibling and a newly selected zero-round `risky` sibling. Human and JSON `next` output identify the risky sibling, report `awaiting-first-review`, `risk_class = risky` and `required_streak = 2`. Red mutations that choose declaration/lexical order, the latest round, the first unconverged round group or the old sibling fail.
8. A round for either convergence identity with no declaration fails closed. A later snapshot mismatch also fails even when every round agrees with that later value; neither a waiver nor the historical cap-adoption boundary suppresses a missing declaration, unresolved selection or mismatch.
9. Current-history migration preserves every existing converged Roadmap and task-loop identity/class, adds no round/escalation/waiver event, changes no Roadmap status, creates no fake active row for retired work, and leaves acceptance/standalone single passes outside convergence declaration joins.
10. Strict metrics validation still rejects a round with no `risk_class`. Fixed-string and drift-guard controls cover the pack guidance, committed AGENTS copies, orchestrator prompts, ledger templates, instrumentation guidance and plan templates; both validation modes, strict render, tests including all red controls, Clippy, diff checks and ASCII checks pass.

### Documentation impact

This semantic change makes the convergence guidance, point-of-action orchestrator prompt, ledger template, instrumentation schema explanation, starter plan template, README workflow-check/`next` description and changelog stale; all are explicit implementation paths above. The generated AGENTS and starter-template copies move with their pack sources. `.agents/workflow.toml` still owns only the class-to-required-streak constants and needs no value change: Q-83 and this repair change which plan declaration selects a class, not what each class requires. `review-loop-class-inheritance` is updated in this planner fold so Q-80 applies to both declaration arms. `review-loop-foreclosure-enforcement`, `workflow-loop-visibility` and `workflow-driver-typed-fleet` are updated to consume the declaration/selection substrate rather than duplicate its joins or selectors.
