## Success Criteria

- One command, run from any working directory and targeting any `--output-dir`, drops the minimal core (a usable `AGENTS.md`, a planning-document template, and the core prompts) into both an empty directory and an existing repository. Writes are off unless confirmed: a run previews the plan and only writes with `--write` or the selector's Save confirmation (`--dry-run` previews explicitly), so nothing is written by accident.
- By default it creates only absent files and never modifies existing ones; `--force` is required to overwrite; a default re-run therefore reverts nothing.
- The user can choose which principles and modules to include, interactively with sane defaults or non-interactively via flags or config.
- The dropped assets are immediately usable to run one pass of the workflow (plan -> review -> implement -> review) without further setup.
- Optional modules can be added without touching or complicating the core.
- The tool can scaffold from a user-supplied template pack, not only the built-in one.
- The scaffolded workflow is internally consistent: `pack/AGENTS.md`, the prompts under `pack/prompts/`, the README diagram, and this plan state the same rules the same way, and the convergence accounting (round outcomes and the single escalation cap) is deterministic and computable from the review ledger alone.
- The self-scaffolded copies stay reliably in sync with the pack: editing a `pack/` file and running a plain `cargo build` (no manual `cargo clean`) re-embeds the change, so `scaffold-self` and the golden sync-test regenerate from the current pack, not a stale embedded one.
- The human-interface layer is present: onboarding (a "Getting started, for the human" section that points to the editable kickoff prompt in `.agents/user-prompts/` and states the human's ongoing decision duty) and a single living human-decision queue that the orchestrator updates and pushes to the human at every checkpoint.
- The scaffolded workflow carries the human-input contract (every human-input point, escalation, intake, open questions, and clarifying questions, presents options, trade-offs, a recommendation, and reasoning judged against the project's numbered Principles, scaled to stakes) and the always-separate triager rule (the triager is a separate agent, independent of both the producer and the orchestrator, for every review round).
- The scaffolded workflow carries a git-durability-and-recovery discipline: a clean tree before spawning a writer, commit-before-delete for workflow-managed files, own-files-only formatting (no repo-wide formatters or cross-owner `git checkout`), an orchestrator recovery protocol on any kill or interrupt, and destructive validation in scratch. Every spawned agent (the writers and the read-only reviewers, triager, and explorers) runs under capability-tiered isolation (container if available, else worktree, else that discipline), and the orchestrator integrates their outputs onto main.
- Review findings flow through per-agent files that other agents read directly and the ledger references by path, so no finding is lost to orchestrator transcription; the files are committed before the orchestrator deletes them.
- A compaction-prep checkpoint keeps the plan and ledger authoritative for resuming after context loss: before a compaction the orchestrator flushes and commits the plan, the ledger, and the Open-Questions queue and verifies the plan's resume anchor, and on resume state is reconstructed from `AGENTS.md`, the plan, and the ledger.
- Human-invoked user prompts (the kickoff prompt and the compaction-prep prompt) live in their own `.agents/user-prompts/` directory, separate from the role prompts in `.agents/prompts/`, and stay thin triggers that do not duplicate workflow content.
- The workflow offers a human-invokable review entry mode (a fourth entry alongside implement, explore, and question-driven input): a human can review the whole tree or a diff against a named plan's Success Criteria, ad-hoc constraints, or open-ended correctness/quality, and get a committed findings report with a handoff into an implement task, reusing the same reviewers, separate triager, severity scale, and high/critical dismissal recheck as the other review phases.
- Optional verification modules compose on the core without complicating it: a deterministic-checks module (a user-configurable, pluggable lint/format/test/mutation gate over the code, with a read-only checks-reviewer, a `{{modules}}` guidance slot that is empty and byte-identical when no module is enabled, and an optional pre-commit hook), a test-driven module (a separate test-author role and a test-first two-gate profile) that hard-depends on it, and a mutation module that hard-depends on that.
- The scaffolded workflow's reviewer/triager diversity rule spans different models OR harnesses where available, so a user running multiple CLIs is guided to spread reviewers across them to reduce shared blind spots.
- The plan's live skeleton is a structured single source of truth: a `<task>.plan.toml` holds the Roadmap (step status, order, dependencies), the Open-Questions queue (id, status, one-line ask, a `receipt` pointer to the JSONL decision record, typed `folded_into`/`superseded_by` cross-references; the queue's `options`/`chosen` stay in the JSONL decision receipt, not the TOML), the numbered Project Principles, step<->increment links, typed task convergence declarations and exact-step plus Q-81 exact-increment historical plan-review mappings, the ordered phase-bearing active-work carrier, bounded digest-pinned historical ownership rows, and (per Q-46) exemption waivers nested on their step plus the W4 baseline in `[meta]`; the append-only `docs/metrics/workflow.jsonl` holds only genuine events (rounds, escalations, decisions, intakes, dismissals). Typed cross-references replace parametric status strings and guessed loop identity, so a `decided` question, a `blocked_by` step, an active phase/review identity, and a retained malformed historical record are structured fields rather than prose or declaration-order conventions, and `validate --source` checks each resolves.
- `agent-flow render` generates a committed-but-never-hand-edited `<task>.md` from the TOML skeleton plus opaque Markdown prose sidecars, splicing each sidecar verbatim and never parsing prose back into structure, so there is no prose round-trip and nothing to clobber: render writes only the derived `<task>.md`, and a schema violation, an unresolved cross-reference, or a missing sidecar exits non-zero and writes nothing. A do-not-edit banner heads the generated file and names its real sources, and the derived Status line and the status vocabulary are generated (not hand-maintained), so they cannot drift.
- A `render --check` guard re-renders and compares against the committed `<task>.md`, catching both a hand-edit of the generated file and a stale render after a source edit; it warns locally so a forgotten re-render never blocks an in-flight workflow step, and fails hard in CI and in the pre-commit hook so a stale plan cannot land.
- Enforcement is preserved over the migrated data as a parser swap, not a rewrite: W3, W4, W5, and the pause.md catch keep working, reading `Step`/`Question`/waiver shapes and the baseline from the TOML and the escalation evidence from the JSONL, with per-increment convergence intact, the two evidence tiers un-launderable, and W5's record-backed join to a decision-scoped escalation preserved across the two substrates.
- New `round` and `escalation` records carry a structured step/increment id, and W3 and W5 join on it in preference to the lexical `leading_slug` strip for post-migration records, so the over-strip fragility (SE-10/B6) no longer applies to newly logged increments, while pre-migration records continue to join via the leading-slug shim.
- Migrating this repo is safe and reversible: the skeleton and sidecars are built additively while the hand-authored `.md` stays the live source (`[meta].primary = "markdown"`), validated synthetic-pilot-first, shadow-rendered and fidelity-diffed against the current plan, then cut over in a single `git revert`-able commit that sets `primary = "toml"`, renders, and (per Q-46) moves and prunes the historical JSONL waiver/baseline lines; `validate` stays green at every stage, and reverting the cutover restores both the hand-authored `.md` and the pruned JSONL lines.
- The scaffolded default stays coherent: a fresh `agent-flow` run drops a `<task>.plan.toml` skeleton, starter prose sidecar directories, and a rendered `<task>.md` that are internally consistent and `validate`-green, with no `w4_baseline` (so every decision the fresh project makes requires a receipt).
- The shipped pack's prompts and docs describe the same TOML+render+sidecar plan flow the tool actually implements: a freshly scaffolded project's `pack/prompts/*` and `pack/user-prompts/kickoff.md` describe authoring and editing the `.plan.toml` skeleton plus prose sidecars, rendering the generated `<task>.md`, never hand-editing it, and `render --check`ing before commit, with no residual Markdown-only-plan authoring instructions or stale `docs/plans/TEMPLATE.md` references; and the shipped `README.md`, `pack/AGENTS.md`, and `pack/instrument.md` are current with the render architecture (the README documents `render`/`render --check` and `validate --source`, and `instrument.md` documents that every metrics record, the `type:"decision"` receipt included, carries the required `task` field via its preamble).
- The workflow's control constants (the risk-class -> required-clean-streak map, the total-round cap, the backstop severity, the phase/tier orderings, the path templates) are single-sourced in `.agents/workflow.toml`, read by both `validate --workflow` and the driver from one `WorkflowSpec`, so the enforcement checker and the driver cannot disagree about the bar and there is no code/prose duplication (a built-in default equal to today's constants, pinned by assertion, keeps an un-migrated project byte-for-byte unchanged).
- The AGENTS.md control-constant fragment is generated from the same spec via a pack render slot and byte-guarded, so the prose statement of every control constant is derived from the spec the driver executes and the two cannot drift, while the rationale prose stays hand-authored around the slot.
- An advisory, read-only `agent-flow next` reports the current per-unit state, the valid transitions, and the next action as a filled instruction prompt (role prompt + artifact + diff range + findings/ledger paths + Principle reminders), in JSON and human text, recomputed statelessly from the plan + log + ledger + spec each call, and its forward projection of the convergence arithmetic matches `validate --workflow`'s backward computation on the same files.
- The driver is non-blocking in-loop (skipping the tool never deadlocks the workflow), consumes agent/human judgment only as typed inputs and never manufactures a verdict, and hard enforcement exists only via an opt-in boundary gate (`validate --workflow --strict` in CI or a pre-commit hook) at the landing boundary rather than per-step.
- Each canonical rule and constant lives once in `pack/AGENTS.md` and the pack prompts/docs point to it rather than restating it: the type-A copies the audit found (the total-round cap value, the clean-round counts and risk-class definition, the findings-file filename templates, the four-level severity scale and its absolute-rating gloss, and the isolation tier order) are replaced by references, the type-B role-scoped procedure prose is kept, and the two type-C accuracy bugs (the README W3-absolute waiver omission and the treefmt-v2 caveat's missing single owner) are fixed.
- Documentation currency is a core cross-cutting part of the workflow: the planner assesses which docs and prompts a folded change makes stale (stated in the planner duties and `pack/AGENTS.md` phase 2), the implementer updates them, the reviewer verifies, and acceptance carries a doc-currency check that a shipped change leaves no doc or prompt stale, with no new role or optional module added.
- The workflow performs a light, stakes-scaled task-entry re-grounding before starting a step and on resume: the orchestrator writes a brief (what the task is, why it exists, the cited durable evidence including the decision receipt, and what it is about to do) sourced only from the durable artifacts (never conversation history) and pushes it for a go/no-go via the human-input contract; and a step carries structured provenance links to the decisions, findings, and commits that justify it, which `render` presents as why the step exists.
- The Q-58 output experiment is run from the retained ablation design against freshly measured `next` output. Before any trial result is generated or read, it commits a frozen protocol fixing the non-inferiority/equivalence margin, confidence level and interval/test method, state/trial aggregation and weights, cross-model aggregation, disagreement/tie rule and analysis command; retained aggregates plus that command mechanically reproduce the plateau and proposed carrier. The frozen non-inferiority/equivalence procedure decides plateau membership. Descriptive marginal/per-arm confidence intervals, their overlap and point estimates never decide admission; an exact precommitted paired confidence bound may implement the frozen rule, as may the precommitted paired hypothesis-test alternative. The result reports task-success against token cost with the oracle-circularity limit intact and produces a human-decided compact carrier before the resume transient, Q-59 currency signal or typed driver fleet is implemented; the one historically sourced output count and every other fixed byte total remain evidence, never a current target.
- TOML-primary waiver guidance has one shipped canonical source: it directs an authorised exemption to nested `[[step.waiver]]`, preserves the record-backed join to a real JSONL escalation, and labels `type:"waiver"` JSONL records as legacy Markdown-primary input only, so a fresh event log contains no inert waiver record.
- Every live convergence-loop class has one authoritative typed plan declaration selected before round one. Roadmap plan/work review uses exact `[[step.increment]].risk_class` plus required phase; task plan review uses unique `[[task_loop]]`; migration-only Q-81 Roadmap-increment and exact step-slug plan review use digest-pinned non-active historical rows; phase remains part of every round, escalation, reconstruction, and active identity. One current-history fixture accounts for all 99 plan-review records exactly once: 63 Roadmap-resolving records over 18 identities partition into seven exact-step records, 41 Q-81 historical increment records with their three exact escalation boundaries, and 15 records on three live plan-review increment declarations; 36 non-Roadmap records resolve through fourteen exact task declarations. `decision-folder-currency-fold` has its own low-risk plan-review increment declaration, while `q77-fold` and `step-intent-fold` are registered real non-Roadmap tasks with low-risk task declarations. Q-81's thirteen existing live delivery increments keep their ids/classes and are declared `work_review`; no new delivery id or history rewrite is permitted. Canonical and exact owner-matching legacy increment ids remain byte-exact. Missing/ambiguous declaration, registration, selector, selection, phase, or snapshot match fails closed before arithmetic; `next` reads the exact live selection before round one and never guesses siblings/phases. Rebuilds inherit through the applicable live declaration unless durably narrowed under a new identity, so a rebuild or phase change cannot silently buy a cheaper bar.
- `validate --workflow` and `next` share one ordered typed review-process reconstruction. Its `Convergence` variant alone applies exact-phase escalation resets, declaration/snapshot joins, convergence-first precedence, foreclosure, and cap; its `SinglePass` acceptance/review variant has no constructible class, streak, foreclosure, or cap but retains the high/critical dismissal re-check. Bounded Q-81 Roadmap-increment plan-review, exact-step plan-review, and malformed unowned-work-review histories are non-active diagnostics: Q-81 history preserves its exact 41 rounds and three escalation segments without consuming live work-review declarations; exact-step history alone exposes its pinned legacy peak result to W3; unowned work history cannot satisfy convergence. The seven-round `q78-design-pass` plan-review segment remains append-only under its digest-pinned adoption boundary through record 386, while every record selected by `task == "q78-design-pass" && phase == "acceptance"` remains outside that window regardless of appended ordinal. Any new event that tries to extend a bounded historical category fails rather than remaining accepted/unjoined.
- The Q-78 step-intent design is internally executable: migration prose sources resolve only to the rendered plan or the step's own historical sidecar, decision sources identify one exact `<commit>:docs/metrics/workflow.jsonl#L<line>` receipt whose `task` matches the step, the entire metrics log is never admitted as relevant, and the paragraph-valued recommendation, design-residual pointer and reproducible decision selectors agree across the question, exploration and owning step. The same pass schedules the drift handover's authored openings and documents `validate`'s missing-explicit-source exit change in the changelog without inventing a README update.
- `next` reads a typed ordered active-work union whose task arm distinguishes task plan review from single-pass acceptance/review, whose question arm represents real exploration independently of Roadmap status, and whose step arm distinguishes live exact-increment plan review from exploration/implementation/work review and can select neither Roadmap plan-review history type nor change recorded phase or guess identity. The orchestrator alone advances explicit transitions; every unit projects once and one selected action copies from the collection. Pending ready/blocked fallback remains until Stage 3. The later fleet consumes the reviewed reconstruction as disjoint `ReviewProcess::{Convergence, SinglePass}` plus nested task/question/step machines; compile-time structure prevents single pass from acquiring convergence fields. Q-82 supersedes real-parallelism gating only for that typed fleet and the focused read-only scheduler. The scheduler's frontier is exactly `not-started`/`next` steps with complete/skipped blockers, explicit actions take precedence, and it proposes without spawning or writing; write-path and authoritative-driving evidence gates remain.
- The in-progress `workflow-calibration` step records Q-85's route decision and Q-88's exact six-option cap-decision receipt, keeps Q-86 `open` against the narrowed synthesis at `docs/plans/workflow-calibration.explorations/Q-86-synthesis.md`, and leaves the current workflow and code unchanged. The proof must model arbitrary finite finding maps soundly, cross-family serious carry, scope and dismissal products, global family identity, fresh evidence, legacy adoption, both terminal floors, and every selected-option transition and bound, and it must close every applicable valid verdict from the five Q-86 synthesis triages through a traceability matrix, executable assertions, and mutation controls.
