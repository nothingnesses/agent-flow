## Findings

### Finding 1 - the new traceability-to-manifest join is not observable in the traceability command's specified contract, and no specified input supplies the mutation run's result

- **Severity:** low.
- **Evidence.** Fix 2 requires the traceability checker to resolve each executable row's named mutation "to exactly one entry in the mutation manifest and to that run's result" and to fail a surviving or unexercised entry (`docs/plans/agent-scaffold.steps/bounded-convergence-option-b-proof.md:184`; same requirement at `:41` and acceptance criterion 11 at `:228`). The exact command that runs the checker passes it only the matrix and the five retained triages, with no manifest or results argument (`:206`). The mutation run is a separate, later invocation (`:207`), whose results the checker cannot read: each invocation gets a fresh external temporary state that is removed after its two-pass comparison, and the whole repository tree must be byte-identical before and after all ten invocations (`:212`), while mutation controls may never write the live tree (`:196`). The expected-output contract for the traceability command was not extended either: it still pins only `valid_findings=51` and `unresolved=0`, and the drift sentence lists only verdict, triage-input, and matrix-row changes as things that must fail it (`:210`). Acceptance criterion 13 accepts the run on those "identical semantic summaries" (`:230`).
- **Reasoning.** A traceability checker that silently skipped the new manifest join, or resolved a name to a manifest entry without checking its result, would still satisfy every output the plan pins for that command, so the specified acceptance evidence cannot detect the absence of the check that fix 2 exists to add. This is the same class of gap round-5 T2 raised (a claimed mutation attribution that nothing binds to a real, killed mutation), reappearing one level up in the fix's own verification contract. The impact is bounded: acceptance criterion 11's prose still states the duty and the mutation command independently enforces manifest-wide coverage (`:39`, `:207`), so this is a traceability-verification gap rather than a loss of mutation coverage, which matches the low severity T2 itself carried.
- **Suggested correction.** State how the checker obtains manifest results (an added input path, or an explicit statement that the checker imports and exercises the manifest in process), and extend the traceability command's expected contract at `:210` with the join's reported outcome, for example a `mutation_rows_resolved=<n>` / `unresolved_mutations=0` summary that an unknown, surviving, or unexercised name must change or fail.

### Finding 2 - the provenance entry added to the scheduler step uses a repository-root path, contradicting the task-relative convention the same commit follows on the proof step

- **Severity:** low.
- **Evidence.** The fix added the same triage file to two steps' provenance in two different forms: `docs/plans/agent-scaffold.plan.toml:1782` records `"docs/plans/agent-scaffold.reviews/q86-decision-r5-triage.md"` on `workflow-ready-frontier-scheduler`, while `:1806` records `"agent-scaffold.reviews/q86-decision-r5-triage.md"` on `bounded-convergence-option-b-proof`. `Provenance.findings` is documented as holding task-relative paths (`src/plan/source.rs:245`), that is, paths resolved from the plan directory `docs/plans/`, so the first form resolves to `docs/plans/docs/plans/agent-scaffold.reviews/q86-decision-r5-triage.md`. Round-5 triage T4 settled exactly this convention when it dismissed the converse claim (`docs/plans/agent-scaffold.reviews/q86-decision-r5-triage.md:58-63`: "`Provenance.findings` holds task-relative paths ... The neighboring full-root-looking reference does not establish a different schema contract"), so this applies that verdict rather than re-raising it. Validation does not catch it: the field is shape-checked by `is_safe_sidecar_ref` only, never resolved (`src/plan/source.rs:643-649`, `:480`), which is why `validate --source` stays green. The projection surfaces both forms on adjacent Roadmap rows (`docs/plans/agent-scaffold.md:304-305`).
- **Reasoning.** The pointer is never dereferenced by a tool, so nothing breaks mechanically; the cost is that a human or an agent following the step's "why this step exists" projection from the plan directory gets a path that does not exist, and the same evidence file is cited two incompatible ways in one commit. The step's three pre-existing entries at `:1779-1781` carry the same defect and are outside this closure's scope; the newly authored line is not.
- **Suggested correction.** Change `:1782` to `agent-scaffold.reviews/q86-decision-r5-triage.md` and re-render. Normalising the three pre-existing sibling entries at `:1779-1781` in the same pass is optional and would remove the intra-list inconsistency the single-line fix leaves behind.
