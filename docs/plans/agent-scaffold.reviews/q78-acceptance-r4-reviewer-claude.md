## Remaining shortfalls

### A. `high` - the Q-83 migration cannot declare two of this repository's own converged increment identities, so the fail-closed rule it introduces has no satisfiable state on this tree

The repair's migration instruction is explicit and doubly constrained: "Existing Roadmap work-review histories are migrated by declaring their exact retained increment identities and observed classes in the plan before enforcement is switched on; the append-only round log is not rewritten" (`docs/plans/agent-scaffold.steps/structured-risk-class-source.md:9`), and "add any missing historical Roadmap increment declarations without renaming converged increment identities, changing statuses or rewriting the event log" (`:20`). Criterion 6 requires the migration to preserve "every existing converged Roadmap increment id and class" (`:35`), and criterion 3 closes every escape: "A round for a Roadmap increment with no declaration fails closed ... neither a waiver nor a historical cap-adoption boundary suppresses a missing declaration or mismatch" (`:32`). SC 37 states the same fail-closed rule as the shipped promise, and `review-loop-foreclosure-enforcement.md:25` re-states it as a data fault evaluated before any convergence arithmetic.

TWO REQUIRED DECLARATIONS ARE UNAUTHORABLE. `docs/metrics/workflow.jsonl` lines 53-57 carry five `work_review` rounds under `task` `round-log-core-incA` (2 rounds, `low_risk`) and `round-log-core-incB` (3 rounds, `risky`). They are pre-migration records with no structured `step`/`increment` fields, so they join by `leading_slug(task)` (`src/workflow.rs:440-447`) to Roadmap step `round-log-core`, which is `status = "complete"` with `increment = []` (`docs/plans/agent-scaffold.plan.toml:512-519`). Their increment identity is therefore the full task string, uppercase suffix included. But `[[step.increment]].id` is held to `is_kebab_case_token` (`src/plan/source.rs:540-545`), which forbids ASCII uppercase (`:465-471`).

REPRODUCED, in scratch: a plan declaring those two exact ids under `round-log-core` exits 1 from `validate --source` with

```
increment id `round-log-core-incA` is not a well-formed kebab-case id
increment id `round-log-core-incB` is not a well-formed kebab-case id
```

The tool's own comment names this very identity as the reason the two id classes differ: orphan-task tokens "may carry an uppercase `-incA` suffix, so this is not lowercase-only ... Step slugs and increment ids are held to the stricter lowercase `is_kebab_case_token`" (`src/plan/source.rs:452-456`), with `round-log-core-incA` quoted at `:465-468`. A scan confirms these are the only two of the 97 log increment identities that join a Roadmap step and fall outside `[a-z0-9-]`.

WHY THIS IS NOT ALREADY OWNED. The measurement exists in the plan, inside `Q-70`'s ask, where the same fact is recorded as a constraint on a WAIVER-ownership direction ("the `-incA` / `-incB` form the round log actually uses ... CANNOT BE DECLARED AT ALL", `docs/plans/agent-scaffold.plan.toml:2285`). No step owns the increment-id contract: `grep -rn "kebab"` over `docs/plans/agent-scaffold.steps/` and the Success Criteria returns nothing, and `structured-risk-class-source.md:19` scopes its `src/plan/source.rs` change to carrying the declared increment map. So the connection to the Q-83 migration is unmade.

THE CONSEQUENCE, which is why this is `high` rather than a nit: an implementer executing the step as written reaches a state with no legal exit. Declaring is refused by the schema; renaming to lowercase is forbidden by `:20` and would silently break the join to an append-only log that `:9` forbids rewriting; rewriting the log is forbidden; a waiver or the cap-adoption boundary is forbidden by criterion 3. The remaining move is an unplanned, unreviewed widening of an id contract on the safety-relevant enforcement path, or `validate --workflow` fails permanently on this repository the moment the step lands, taking the pre-commit and CI gates with it. This defeats the criterion Q-83 exists to establish, and it is the highest-severity pass-3 repair that it defeats. It is not `critical` because it fails loud at implementation time rather than admitting a false green.

SMALLEST SAFE DISPOSITION. Decide the id contract inside this step and state it: either hold increment ids to `is_well_formed_token` (which the log's real identities and `[meta].orphan_tasks` already satisfy) and keep uniqueness/lowercase only where a slug demands it, or add a declared, digest-pinned legacy-identity mapping alongside the declarations. Either way, name `round-log-core-incA` and `round-log-core-incB` as fixtures, add a red control that the pre-migration join still resolves after the change, and correct criterion 6, which today asserts a preservation that the schema refuses.

### B. `medium` - task-scoped convergence loops have no declarable class home, so the same pass enforces a bar it computes from the snapshot Q-83 declares non-authoritative

SC 37 opens "Review-loop risk class has one authoritative structured home: `[[step.increment]].risk_class`", and the sidecar closes the alternatives: "No reader recovers a missing declaration from the ledger or the first round" (`structured-risk-class-source.md:7`). Its only stated exemption is for records that are not convergence loops at all: "Task-scoped single-pass records and other records that are not Roadmap increments remain event snapshots" (`:9`).

TASK-LEVEL PLAN REVIEW IS NEITHER. `review-loop-foreclosure-enforcement.md:7` gives it a first-class loop identity ("a task-level plan-review loop uses its registered task plus `plan_review`") and scopes the declaration rule to the other arm ("Within a Roadmap increment window, read the authoritative class from its Q-83 plan declaration"). The same step then enforces the cap and the foreclosure inequality `k - r < q - c` (`:5`) over those windows and says so twice: "preserves fail-loud enforcement for future Roadmap and non-Roadmap loops" (`:15`) and "Future non-Roadmap task loops are enforced rather than silently skipped" (criterion 6, `:28`). The required streak `q` in that inequality is a function of the class, so for every task loop the class is load-bearing and its only available source is `round.risk_class`, which SC 37 demotes to "a required auditable snapshot".

THE HOME DOES NOT EXIST STRUCTURALLY. Increments nest under a step (`increments: Vec<Increment>` on `Step`, `src/plan/source.rs:153-155`), and the only other registry for these tasks carries no class: `orphan_tasks: Vec<String>` (`src/plan/source.rs:107-110`).

THE POPULATION IS REAL, NOT HYPOTHETICAL. Reproduce with `jq -r 'select(.type=="round") | [(.increment // ""), (.step // ""), .task, .risk_class, .phase] | @tsv' docs/metrics/workflow.jsonl` and resolving each record's step as the structured `step` else `leading_slug(task)`: 20 logged loop identities resolve to no Roadmap step, and several are multi-round convergence loops whose class already selects their bar, including `q78-design-pass` (7 `plan_review` rounds, all `risky`), `q70-capture` (3, `risky`), `step-intent-fold` (6, `low_risk`), `plan-fold` (4, `low_risk`) and `q77-fold` (4, `low_risk`). `q78-design-pass` is the exact window `review-loop-foreclosure-enforcement.md:11` builds its adoption boundary around, so the pass has already reasoned about this population without giving it a class of record.

IMPACT. Two live-together statements: "one authoritative structured home" and "first-round authority is closed" are false for every task loop, and a future orchestrator can still open a plan-review loop, log `low_risk` on round 1 of a genuinely risky plan artifact, and converge at one clean round with every validator green. That is the R3-1 defect surviving in the population the same pass newly brings under enforcement. It is `medium`, not `high`: it neither corrupts data nor blocks work, and it is a continuation of today's behaviour rather than a regression, but it makes an acceptance criterion overstate what ships.

SMALLEST SAFE DISPOSITION. Either give a task loop a declared class home (a typed loop declaration keyed by the registered task, or `[meta].orphan_tasks` entries promoted from strings to tables with a class), or state plainly in SC 37 and in `structured-risk-class-source.md:9` that task-scoped convergence loops keep their round snapshot as the class of record, with the reason, and narrow SC 37's "one authoritative structured home" to the Roadmap-increment population. Pin whichever choice with a task-loop fixture in `review-loop-foreclosure-enforcement`'s table tests.

### C. `medium` - nothing identifies which declared increment's loop is open before its first round, so the pre-round-one criterion is unimplementable for the plan's multi-increment steps

Criterion 4 requires that "Before round one, human and JSON `next` output for a declared `risky` increment reports `risk_class = risky` and `required_streak = 2`", with red controls that restore nulls (`structured-risk-class-source.md:33`), and the model says the declaration is made "at loop open, before spawning the first reviewer" (`:7`). Both sentences assume one identifiable open increment. Three facts on this tree defeat that assumption.

1. DECLARATION IS NOT A LOOP-OPEN SIGNAL HERE. Nine steps already declare more than one increment, and they declare them long before any of those loops open: `step-intent-encoding` is `not-started` and declares eight, `validation-constraints` is `not-started` and declares six while only `-inc1` has any rounds, `workflow-driver` is `in-progress` with three. So the presence of a declaration cannot mean "this loop is open".
2. THE NEW CARRIER DOES NOT CARRY IT. The step arm added by the same pass is "a resolving Roadmap `step` plus one of `exploration`, `implementation` or `work_review`" (`workflow-loop-visibility.md:11`) with no increment field, so the typed active-work union cannot name the open increment either.
3. THE SHIPPED SELECTOR DERIVES THE INCREMENT ONLY FROM ROUNDS (`src/next.rs:864-885`), so before a new increment's first round it returns the previous one.

REPRODUCED, in scratch: an `in-progress` step `multi` declaring `multi-inc1` `low_risk` and `multi-inc2` `risky`, with one `clean` `low_risk` round for `multi-inc1` and none for `multi-inc2`, yields

```
"increment": "multi-inc1", "state": "converged", "risk_class": "low_risk", "required_streak": 1
```

and `validate --workflow` reports `workflow invariants hold`. There is no input anywhere in the plan or the log that would make either consumer report `multi-inc2`'s declared `risky` and its streak of 2, which is exactly the output criterion 4 demands. An implementer must invent the selection rule, and the cheapest inventions (first declared, or last round's increment) both report a converged or wrong increment for the shape the plan itself uses most.

IMPACT. `medium`: it makes a criterion of the pass's `high`-severity repair unmeasurable for nine of the plan's own steps, including the two the Q-78 design pass authored, and an invented selector reports a stale class exactly when a new risky loop opens, which is when the bar matters most. No data is lost and the error is visible in output rather than silent in enforcement.

SMALLEST SAFE DISPOSITION. Define the open-increment rule inside this step (for example the lowest-declared increment with no converged window, or an explicit increment id on the `[[active_work]]` step arm, which also gives the orchestrator the loop-open operation the model assumes) and pin a multi-increment pre-round fixture plus a red control that returns the converged increment. Reconcile "declared at loop open" with the plan's practice of declaring every increment up front, so the timing claim matches what the criterion can check.
